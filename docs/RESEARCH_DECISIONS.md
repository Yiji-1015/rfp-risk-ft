# 연구 설계 및 데이터셋 결정 기록

> 기준일: 2026-08-12  
> 목적: 데이터셋 구축과 실험 과정에서 확정한 결정, 근거, 구현 규칙을 논문 작성에 재사용할 수 있도록 기록한다.

> **문서 역할:** 합의가 끝난 방법론 결정의 단일 기준 문서다.  
> **권위 수준:** 데이터셋 단위, 스키마, 추출, 전처리와 모델 입력에 관해서는 이 문서를 우선한다.  
> **수정 시점:** 결정을 새로 확정하거나 실험 근거에 따라 기존 결정을 변경할 때 수정한다. 단순 아이디어는 먼저 [`PROJECT_DIRECTION.md`](PROJECT_DIRECTION.md)의 열려 있는 결정에 기록한다.

이 문서는 단순 작업 로그가 아니다. 결정이 바뀌면 기존 내용을 지우지 않고 변경 이유와 새 버전을 기록한다. 아직 실험으로 확인하지 않은 내용은 결과가 아니라 가설로 표현한다.

## 1. 데이터셋 분석 단위

### 결정

```text
요구사항 ID 하나 = 데이터 행 하나 = 모델 예측 하나
```

- 요구사항 내부의 세부 불릿은 독립 행으로 분할하지 않는다.
- 정의, 조건, 예외, 수량과 책임 범위를 하나의 요구사항 문맥으로 함께 보존한다.
- 목표 행 수를 미리 정하지 않는다. 원문에서 검증된 요구사항 수를 최종 행 수로 사용한다.

### 근거

세부 불릿을 분리하면 동일 요구사항 안의 조건과 예외가 서로 떨어져 의미가 달라질 수 있다. 실제 사용자가 검토하고 대응하는 단위도 요구사항 ID이므로 학습과 예측 단위를 이에 맞춘다.

### 논문 반영 위치

- 연구 방법: 분석 단위와 데이터 구축 절차
- 한계: 긴 요구사항 내부에 여러 위험 요인이 함께 존재할 수 있음

## 2. 요구사항 데이터의 최소 스키마

### 결정

요구사항 원본 데이터는 다음 7개 열을 사용한다.

| 열 | 의미 |
|---|---|
| `requirement_uid` | 문서와 원문 ID를 결합한 전역 고유키 |
| `document_id` | RFP 문서 식별자 |
| `requirement_id` | 원문 요구사항 번호 |
| `requirement_type` | 기능, 성능, 보안 등 원문의 요구사항 분류 |
| `requirement_name` | 원문 요구사항 명칭 |
| `raw_text` | 요구사항 본문 전체 |
| `review_status` | 추출 결과의 검수 상태 |

### 부가정보 관리

- 원문 위치, 파일 해시, 추출기 버전 등 감사 정보는 학습용 주 테이블에 반복 저장하지 않고 별도 감사 자료나 실행 기록에 보관한다.
- `requirement_uid`는 여러 문서에 반복되는 `SFR-001` 등의 ID를 안전하게 연결하기 위해 유지한다.

### 논문 반영 위치

- 데이터셋 설명
- 재현성 및 데이터 계보 관리

## 3. 요구사항 추출 전략

### 결정

RFP별 정규식만 나열하지 않고 다음 순서의 구조 기반 추출을 사용한다.

```text
HTML 표 파싱
→ 셀 라벨 정규화
→ 요구사항 ID 기준 레코드 감지·분리
→ 공통 스키마 매핑
→ 자동 무결성 검사
→ 예외만 사람 검토
```

공백, 줄바꿈과 `<br>` 차이를 제거한 뒤 다음과 같은 의미 라벨을 인식한다.

- 요구사항 분류
- 요구사항 고유번호
- 요구사항 명칭
- 정의
- 세부내용

문서에 따라 한 HTML 표에 여러 요구사항이 포함될 수 있으므로 `요구사항 고유번호` 행을 기준으로 논리적 블록을 나눈다. 표 첫 행에 ID만 제시되는 형식은 별도 어댑터로 처리한다.

### 자동 검수 항목

- ID, 명칭 또는 본문 누락
- 문서 내부 ID 중복
- 빈 본문
- 목록과 상세표의 불일치
- HTML 잔재
- 비정상적으로 짧은 본문
- 중첩 표 또는 변환 손실 의심 사례

### 현재 구현 확인

- 분석 대상: 공개 RFP 10개
- 추출 요구사항: 1,024개
- 빈 본문: 0개
- 중복 UID: 0개

이 수치는 현재 Markdown 변환본과 추출기 기준이며, 원본 PDF·HWP·HWPX 대조 전 최종 확정 수치로 사용하지 않는다.

### 논문 반영 위치

- 데이터 수집 및 전처리
- 데이터 품질 관리
- 재현성

## 4. 불릿과 텍스트 구조 전처리

### 결정

원문은 보존하고 모델 입력 생성 단계에서 불릿을 정규화한다.

```text
raw_text
→ normalized-list
→ 필요 시 flat 비교본
```

기본 입력은 `normalized-list`로 한다.

- `◦`, `○`, `●`, `•`, `▪`, `■`, `□` 등 줄 시작 불릿을 `-`로 통일한다.
- 목록의 줄 경계는 유지한다.
- `AI-플랫폼`, `1-2년`, 요구사항 ID 등 본문 내부 하이픈은 보존한다.
- 숫자, 금액, 기간, 비율, 영문 약어는 삭제하지 않는다.
- 원문 단어를 요약하거나 다시 쓰지 않는다.

### 근거

문서 구조를 보존하는 태그와 계층 정보를 활용했을 때 문서 분류 또는 독해 성능이 향상된 선행연구가 있다. 반면 RFP마다 다른 불릿 문자를 그대로 사용하면 문자 기반 모델이 문서 또는 기관의 서식 차이를 학습할 수 있다. 따라서 불릿의 종류는 통일하되 목록 경계는 보존한다.

직접적으로 “RFP 불릿 유지 대 제거”를 검증한 선행연구는 확인하지 못했다. 따라서 불릿 정규화의 효과는 선행연구의 확정 결론이 아니라 본 연구 데이터에 적합한 설계 가설이다.

### 현재 구현 확인

- 10개 문서에서 문서당 2개, 총 20개 요구사항 표본 생성
- 원본 용량이 가장 큰 `국방 지능형 플랫폼 고도화 구축` RFP 전체 169개 요구사항 처리
- 해당 문서에서 불릿 정규화가 발생한 행: 161개
- 줄 시작 미처리 특수 불릿: 0개
- 빈 전처리 결과: 0개

### 발견된 한계

PDF·HWP 변환 과정에서 중첩 표의 셀 경계가 붙을 수 있다. 예를 들어 표가 다음처럼 평탄화될 수 있다.

```text
연번기능용도수량
1WEBWEB 서버12
```

이는 불릿 정규화 문제가 아니라 원문 변환 및 표 추출 문제다. 표 셀 경계 보존 규칙과 원본 대조가 별도로 필요하다.

### 관련 선행연구

- Maillette de Buy Wenniger et al. (2020), *Structure-Tags Improve Text Classification for Scholarly Document Quality Prediction*
- Wan et al. (2021), *Does Structure Matter? Encoding Documents for Machine Reading Comprehension*
- Camacho-Collados and Pilehvar (2017), *On the Role of Text Preprocessing in Neural Network Architectures*
- Karimi et al. (2021), *AEDA: An Easier Data Augmentation Technique for Text Classification*

### 논문 반영 위치

- 선행연구: 문서 구조와 전처리
- 연구 방법: 텍스트 정규화
- 실험 또는 부록: `raw`, `normalized-list`, `flat` 생성 규칙

## 5. 모델 입력에 요구사항명 포함

### 결정

모든 학습·임베딩·파인튜닝 입력에 요구사항명과 본문을 함께 사용한다.

```text
요구사항명: {requirement_name}

요구사항 내용:
{preprocessed_text}
```

`raw_text` 자체에 요구사항명을 덧붙이지 않는다. 모델 입력을 생성할 때만 결합한다.

### 근거

요구사항명은 발주기관이 제공한 원문 정보이며 본문의 핵심 주제를 압축한다. 실제 예측 시점에도 사용할 수 있으므로 데이터 누수가 아니다. 연구 범위를 과도하게 늘리지 않기 위해 본문 단독 입력과의 별도 비교 실험은 현재 수행하지 않는다.

### 논문 반영 위치

- 모델 입력 구성
- 데이터 누수 방지 설명

## 6. 위험 분류와 전체 문서 검토의 분리

### 결정

실제 워크플로우를 두 단계로 분리한다.

```text
1단계: 요구사항 단위 국소 위험 분류
→ 2단계: 전체 RFP 문맥을 이용한 검토 및 조정
```

### 1단계: 본 연구의 학습·분류 범위

입력:

```text
요구사항명 + 해당 요구사항 본문
```

출력 후보:

- 통상수용
- 견적반영
- 계약·질의검토

요구사항만으로 알 수 없는 인프라 제공 여부, 전체 일정, 예산, 공통 계약조건은 추측하지 않는다. 필요한 경우 판단 근거에 `정보 부족` 또는 `전체 문서 확인 필요`를 기록한다.

### 2단계: 후속 검토 워크플로우

1단계에서 선별된 위험 후보를 중심으로 전체 RFP에서 다음 문맥을 확인한다.

- 발주기관 제공 인프라와 데이터
- 전체 사업기간과 단계별 일정
- 예산과 수량
- 공통 검수·성능 조건
- 무상지원, 유지보수와 책임 범위
- 다른 요구사항에 기재된 예외와 완화 조건

확인 결과에 따라 1단계 위험을 완화하거나 상향할 수 있다.

### 예시

```text
요구사항 단독: GPU 서버 구축 → 견적반영
전체 문서 확인: GPU 서버를 발주기관이 제공 → 위험 완화 가능
```

```text
요구사항 단독: 일반 성능시험 → 통상수용
전체 문서 확인: 검수 기준 불명확, 실패 시 무상 재수행 → 계약·질의검토로 상향 가능
```

### 연구 타당성 규칙

LLM 라벨러와 후속 학습 모델은 같은 정보를 봐야 한다. 요구사항 단위 모델을 학습할 때 LLM 라벨러에게 전체 RFP 문맥을 제공하지 않는다. 전체 문서를 보고 만든 라벨을 요구사항 본문만 보는 모델에 학습시키면 입력 정보가 불일치하고 라벨을 재현할 수 없기 때문이다.

### 논문용 범위 문장

> 본 연구는 개별 요구사항에 명시된 국소적 위험을 분류하며, 문서 전역의 조건에 따른 최종 위험 조정은 후속 검토 단계로 분리한다.

### 논문 반영 위치

- 연구 문제와 적용 범위
- 라벨링 프로토콜
- 실제 활용 워크플로우
- 연구 한계와 후속 연구

## 7. 요구사항 데이터셋 v0.2.0 동결

### 결정

요구사항 데이터셋 `requirements_v0.2.0`을 1,024행으로 동결하고 LLM 라벨링 파일럿 입력으로 사용한다.

- 요구사항명 누락, 본문 누락과 중복 UID는 0건이다.
- 목록-상세 ID가 있는 9개 문서 중 7개는 완전 일치한다.
- 국방 목록 중복과 KAC 목록 전용 항목은 원문 예외로 승인한다.
- 남동발전 개수표 99건과 상세표 101건의 차이는 원문 예외로 기록하고 상세표를 기준으로 한다.
- 문서별 첫·중간·마지막·최장 본문 총 40행을 Markdown과 대조했다.
- 인천공항의 이중 하이픈 ID는 `source_requirement_id`에 보존하고 목록 기준 canonical ID를 `requirement_id`로 사용한다.
- 중첩표의 행은 줄바꿈, 셀은 ` | `로 직렬화해 셀 경계를 보존한다.

### 예외 처리 원칙

- 목록 중복은 상세 본문을 중복 행으로 만들지 않는다.
- 목록에만 있고 상세 본문이 없는 요구사항은 추정하거나 생성하지 않는다.
- 원문 ID를 정규화할 때 원문 값을 별도 필드에서 삭제하지 않는다.
- 원문의 개수표와 상세표가 다르면 상세 요구사항을 학습 행의 근거로 사용하고 차이를 감사 보고서에 남긴다.

### 논문 반영 위치

- 데이터 품질 감사와 예외 처리
- 데이터 계보 및 재현성
- 데이터셋 한계

## 9. Pure TF-IDF 앵커 검색기 및 In-Memory 검색

### 결정

Dynamic Few-shot 앵커링 시 별도의 무거운 외부 벡터 DB(Chroma, Qdrant 등)나 딥러닝 임베딩 모델 서버 없이, Pure TF-IDF 및 `scikit-learn` 기반 코사인 유사도 연산으로 앵커를 동적 인출한다.

- 희소 벡터(Sparse Vector) 표현: 어절(Word) 1~2gram 및 자소/문자 n-gram 결합
- `sublinear_tf=True`를 적용하여 고빈도 단어의 편향을 완화
- In-Memory 상에서 $O(N)$ 코사인 유사도 즉시 연산 (1,024건 대상 < 0.001초)

### 근거

소규모 RFP 요구사항 데이터셋 특성상 특정 계약/기술 독소 키워드(`무상`, `지체상금`, `250TB`, `K-RMF`, `상주`)의 정확한 일치(Lexical Match)를 잡는 것이 실무 위험 판정에 가장 직관적이고 효과적이다. 외부 인프라 부하 없이 독립 실행이 가능하다.

---

## 10. Dynamic Few-shot 앵커링 시 데이터 누수 하드 차단

### 결정

Dynamic Few-shot 프롬프트를 구성할 때 Target 요구사항의 출처 문서와 동일한 `document_id`를 가진 앵커는 유사도 계산 대상에서 하드 필터링(`similarities[idx] = -1.0`)하여 제외한다.

```python
# target과 동일한 document_id를 가진 앵커는 자동 차단
if anchor.get("document_id") == target_doc_id:
    similarities[idx] = -1.0
```

### 근거

동일 RFP 문서 내부의 다른 요구사항을 앵커 예시로 주입할 경우, 기관 고유의 서식이나 문맥이 그대로 유입되어 평가(Validation/Test) 시 문서 단위 일반화 성능을 왜곡할 수 있다.

## 11. 3개 대표 RFP 기반 1차 라벨링 비교 파일럿

### 결정

전체 1,024건 라벨링에 앞서 대표 성격의 RFP 3개 문서(총 259건)를 선별하여 Zero-shot vs Pure TF-IDF Dynamic Few-shot 비교 파일럿을 먼저 수행한다.

- 대상 문서: `kac_ai_work_platform` (86건), `incheon_airport_digital_work` (78건), `ccrs_ai_platform` (95건)

### 근거

공공 SI 수주 현실상 불합리해 보이는 문구라도 10개 기관 공통 관행인 조항(통상수용)과 특정 사업의 기습 독소조항(계약검토)을 구분하기 위해, 앵커링 도입 전후의 라벨 변화 양상을 눈으로 직접 확인하고 라벨링 기준을 유동적으로 조정하기 위함이다.

## 12. In-Context Few-Shot 프롬프트 고도화 계획 (llm-wiki 연계)

### 결정

Dynamic Few-shot 앵커 주입 시 단순 예시 나열 방식에서 벗어나, Target 요구사항과 앵커 간의 **공통 핵심 키워드(Overlap Terms)** 및 **TF-IDF 유사도 점수**를 프롬프트 구조에 함께 포함시키는 고도화 방안을 후속 파이프라인에 반영한다.

### 근거

인-컨텍스트 학습(In-Context Learning) 시 LLM이 단순히 앵커의 정답만 모방하는 대신, "어떤 키워드 유사성 때문에 이 예시가 인출되었는지" 맥락을 인지하게 만들어 주 라벨 판정의 인과성과 일관성을 극대화하기 위함이다.

## 13. 3개 대표 RFP 라벨링 파일럿(259건) 결과 및 단일 모델 통제 원칙

### 결정

3개 대표 RFP(259건)에 대해 Zero-shot vs Pure TF-IDF Dynamic Few-shot 라벨링 비교 실험을 완수하였으며, 연구의 엄밀성과 통제 변수(Controlled Experiment) 유지를 위해 100% 동일한 단일 LLM(`gemini-3.5-flash-lite`)을 사용하였다.

- **실험 수치 결과**:
  - 대상 문서: `kac_ai_work_platform` (86건), `incheon_airport_digital_work` (78건), `ccrs_ai_platform` (95건)
  - 총 요구사항 수: 259건
  - 라벨 일치 건수: 182 / 259건
  - 전체 라벨 일치율 (Agreement Rate): **70.27%**
  - 판정 변동 건수 (Action Shift): **77건 (29.73%)**

### 연구 인사이트 및 관행 반영 효과

1. **Zero-shot의 과도한 보수적 방어 판정**: Zero-shot 단독 실행 시 기술 난이도가 높거나 모호한 AI/RAG 요구사항(예: RAG 파이프라인 구축, AI 가드레일, 준실시간 평가 모니터링 등)에 대해 54건을 `계약·질의검토`로 과도하게 매핑함.
2. **앵커링(Few-shot) 도입을 통한 현실적 교정**: 타 공공 RFP 앵커 예시 3개가 프롬프트로 주입되자, LLM이 타 공공기관 구축 사업의 일반적인 SI/개발 공수 범위를 학습하여 `계약·질의검토` 54건 중 **26건(48.1%)이 현실적인 `견적반영`으로 교정**됨.
3. **도메인 통상 관행 반영 확인**: "개별 요구사항만 볼 때는 불합리해 보여도 타 기관 공통 관행인 조항"을 앵커 검색이 성공적으로 포착하여, 실무 현장에 적합한 라벨(통상수용/견적반영)을 부여함을 통계 및 질적 사례로 입증함.

### 발견된 한계 및 향후 개선 대책 (Anchor Label Bias)

- **견적반영 라벨 쏠림 현상 관찰**:
  - Dynamic Few-shot 적용 후 `견적반영` 라벨 비율이 **68.7% (178/259건)**로 증가함.
  - **원인 분석**: RFP 요구사항 문항 특성상 공수/비용 관련 항목이 다수이며, Top-k 유사도 검색 시 `견적반영` 앵커 예시가 과다 주입되어 LLM이 리스크 항목을 과도하게 안일하게 순화(Softening Bias)시킬 위험이 관찰됨.
- **향후 개선 대책 (Balanced Stratified Few-shot)**:
  - 앵커 인출 시 단순 유사도 Top-k만 추출하지 않고, **`통상수용`, `견적반영`, `계약·질의검토` 각 3가지 라벨의 대표 앵커를 1개씩 균형 있게 주입(Stratified Selection)**하여 앵커 라벨 편향을 억제하는 고도화 방안을 2차 전체 라벨링 단계에 적용하기로 결정함.

## 14. 학술 선행연구 기반 층화 퓨샷 검색 (Stratified Few-shot Retrieval) 채택

### 결정

Dynamic Few-shot 앵커 주입 시 발생한 68.7% '견적반영' 라벨 쏠림(Majority Label Bias)을 해결하기 위해, 최신 NLP 학술 문헌(Zhao et al., ICML 2021; Fei et al., ACL 2023; Gao et al., ICLR 2025)에서 입증된 **층화 퓨샷 검색(Stratified Retrieval: 라벨별 1:1:1 비율 강제 인출)**을 2차 비교 파일럿 및 전수 라벨링 알고리즘으로 최종 채택한다.

### 학술적 근거

1. **Zhao et al. (ICML 2021, *Calibrate Before Use*)**:
   - In-Context Learning에서 LLM은 프롬프트 내에 가장 자주 나타난 레이블을 맹목적으로 선호하는 **다수 레이블 편향(Majority Label Bias)**을 가짐을 통계적으로 입증.
2. **Fei et al. (ACL 2023, *Mitigating Label Biases for In-context Learning*)**:
   - 전문 도메인 어휘(예: '단가', '산출물', '일정')가 특정 클래스와 결합될 때 발생하는 **도메인-컨텍스트 레이블 편향(Domain-Label Bias)**을 규명.
3. **Gao et al. (ICLR 2025, *Exploring Imbalanced Annotations for Effective ICL*)**:
   - 앵커 예시의 레이블 불균형이 심할수록 LLM의 **작업 학습(Task Learning)** 능력이 파탄나며, 희소 클래스에 대한 위음성(False Negative)이 급증함을 증명.

### 실행 구현 알고리즘

- 코사인 유사도 상위 Top-3를 맹목적으로 추출하는 방식을 폐기하고,
- 앵커 후보 풀을 `통상수용`, `견적반영`, `계약·질의검토` 3개 라벨 인덱스로 분리하여 **각 라벨별로 쿼리와 가장 유사한 앵커를 1개씩(총 3개, 1:1:1 비율) 추출**하여 프롬프트에 제공함으로써 앵커 레이블 편향을 물리적으로 하드 차단함.

## 15. 예측 가능한 API 예산 제어 및 사전 비용 추정 원칙 (Predictable Budget Control)

### 결정

연구 및 데이터 구축 시 무분별하거나 예측 불가능한 API 비용 지출을 원천 차단하기 위해, **사전 비용 추정(Pre-Execution Cost Estimation)** 및 **예산 상한 캡(Budget Safety Cap)** 원칙을 시스템 운영 표준으로 확정한다.

- **사전 비용 계산 및 명시 (Pre-execution Estimation)**:
  - 대량 LLM API 호출 스크립트 실행 전, `(총 요구사항 수 × 프롬프트당 평균 토큰 수 × 모델 단가)`를 계산하여 **총 예상 비용(원화/달러)을 사전 계산하고 명시**한다.
- **예산 상한 캡 및 안전 멈춤 (Budget Safety Cap)**:
  - 사용자가 사전에 허용한 예상 비용 범위를 넘어서는 대규모 파이프라인의 경우, 자동으로 가동을 멈추고 사용자 승인을 받도록 안전 캡(Cap)을 설정한다.
- **투명한 토큰/비용 로깅 (Transparent Cost Logging)**:
  - API 호출 시 실제 소비된 토큰 수와 소요 비용을 실시간으로 추적 및 기록하여 예측 가능하고 신뢰할 수 있는 비용 제어를 보장한다.

## 16. LLM 출력 스키마 최소화 원칙 (Output Schema Minimization)

### 결정

LLM API 호출 시 출력 스키마를 **연구 목적에 실질적으로 필요한 최소 필드**로만 구성한다. 불필요한 장문 서술 필드를 포함시키면 출력 토큰 수가 폭발적으로 증가하여 비용 대비 효용이 현저히 낮아진다.

**확정 최소 출력 스키마 (3개 필드)**:

| 필드 | 역할 | 형식 |
|---|---|---|
| `primary_action` | 핵심 분류 라벨 (연구의 Y) | Enum: `통상수용` / `견적반영` / `계약·질의검토` |
| `confidence` | 라벨 불확실성 지표 | Enum: `높음` / `보통` / `낮음` |
| `reasoning` | 판단 근거 (앵커 재사용) | **1~2문장 요약형**으로 길이 제한 |

### 제거 필드 및 사유

다음 필드는 연구 핵심 목표(라벨 분류)와 직접적 관련이 낮으며, 출력 토큰을 과도하게 소비하므로 제거한다.

| 제거 필드 | 제거 사유 |
|---|---|
| `evidence` | `reasoning`과 90% 이상 내용 중복 |
| `missing_information` | 라벨링 본질과 무관, 논문 한계절 논의로 대체 가능 |
| `domain_dependency` | 라벨 분류 결정에 직접 영향 없음 |
| `risk_factors.cost_driver` | 현 파일럿 단계에서 과잉 분석 |
| `risk_factors.scope_uncertainty` | 현 파일럿 단계에서 과잉 분석 |
| `risk_factors.responsibility_risk` | 현 파일럿 단계에서 과잉 분석 |
| `risk_factors.acceptance_risk` | 현 파일럿 단계에서 과잉 분석 |

### 기대 효과

- 출력 토큰 수: 건당 약 800~1,000 토큰 → **약 80~100 토큰 (약 10배 감소)**
- 이에 따른 출력 비용도 약 10배 절감
- `reasoning`을 1~2문장으로 제한하므로, 앵커 주입 시 프롬프트 길이도 함께 단축됨

### 논문 반영 위치

- 연구 방법: 라벨링 파이프라인 설계 및 출력 구조
- 한계 및 후속 연구: 세부 리스크 요인 분류는 추후 2단계 검토 워크플로우에서 수행
