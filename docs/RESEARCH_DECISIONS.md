# 연구 설계 및 데이터셋 결정 기록

> 기준일: 2026-08-12  
> 목적: 데이터셋 구축과 실험 과정에서 확정한 결정, 근거, 구현 규칙을 논문 작성에 재사용할 수 있도록 기록한다.

> **문서 역할:** 합의가 끝난 방법론 결정의 단일 기준 문서다.  
> **권위 수준:** 데이터셋 단위, 스키마, 추출, 전처리와 모델 입력에 관해서는 이 문서를 우선한다.  
> **수정 시점:** 결정을 새로 확정하거나 실험 근거에 따라 기존 결정을 변경할 때 수정한다. 단순 아이디어는 먼저 [`PROJECT_DIRECTION.md`](PROJECT_DIRECTION.md)의 열려 있는 결정에 기록한다.

이 문서는 단순 작업 로그가 아니다. 결정이 바뀌면 기존 내용을 지우지 않고 변경 이유와 새 버전을 기록한다. 아직 실험으로 확인하지 않은 내용은 결과가 아니라 가설로 표현한다.

## 1. 데이터셋 분석 단위

### 결정

```text
요구사항 ID 하나 = 데이터 행 하나 = 모델 예측 하나
```

- 요구사항 내부의 세부 불릿은 독립 행으로 분할하지 않는다.
- 정의, 조건, 예외, 수량과 책임 범위를 하나의 요구사항 문맥으로 함께 보존한다.
- 목표 행 수를 미리 정하지 않는다. 원문에서 검증된 요구사항 수를 최종 행 수로 사용한다.

### 근거

세부 불릿을 분리하면 동일 요구사항 안의 조건과 예외가 서로 떨어져 의미가 달라질 수 있다. 실제 사용자가 검토하고 대응하는 단위도 요구사항 ID이므로 학습과 예측 단위를 이에 맞춘다.

### 논문 반영 위치

- 연구 방법: 분석 단위와 데이터 구축 절차
- 한계: 긴 요구사항 내부에 여러 위험 요인이 함께 존재할 수 있음

## 2. 요구사항 데이터의 최소 스키마

### 결정

요구사항 원본 데이터는 다음 7개 열을 사용한다.

| 열 | 의미 |
|---|---|
| `requirement_uid` | 문서와 원문 ID를 결합한 전역 고유키 |
| `document_id` | RFP 문서 식별자 |
| `requirement_id` | 원문 요구사항 번호 |
| `requirement_type` | 기능, 성능, 보안 등 원문의 요구사항 분류 |
| `requirement_name` | 원문 요구사항 명칭 |
| `raw_text` | 요구사항 본문 전체 |
| `review_status` | 추출 결과의 검수 상태 |

### 부가정보 관리

- 원문 위치, 파일 해시, 추출기 버전 등 감사 정보는 학습용 주 테이블에 반복 저장하지 않고 별도 감사 자료나 실행 기록에 보관한다.
- `requirement_uid`는 여러 문서에 반복되는 `SFR-001` 등의 ID를 안전하게 연결하기 위해 유지한다.

### 논문 반영 위치

- 데이터셋 설명
- 재현성 및 데이터 계보 관리

## 3. 요구사항 추출 전략

### 결정

RFP별 정규식만 나열하지 않고 다음 순서의 구조 기반 추출을 사용한다.

```text
HTML 표 파싱
→ 셀 라벨 정규화
→ 요구사항 ID 기준 레코드 감지·분리
→ 공통 스키마 매핑
→ 자동 무결성 검사
→ 예외만 사람 검토
```

공백, 줄바꿈과 `<br>` 차이를 제거한 뒤 다음과 같은 의미 라벨을 인식한다.

- 요구사항 분류
- 요구사항 고유번호
- 요구사항 명칭
- 정의
- 세부내용

문서에 따라 한 HTML 표에 여러 요구사항이 포함될 수 있으므로 `요구사항 고유번호` 행을 기준으로 논리적 블록을 나눈다. 표 첫 행에 ID만 제시되는 형식은 별도 어댑터로 처리한다.

### 자동 검수 항목

- ID, 명칭 또는 본문 누락
- 문서 내부 ID 중복
- 빈 본문
- 목록과 상세표의 불일치
- HTML 잔재
- 비정상적으로 짧은 본문
- 중첩 표 또는 변환 손실 의심 사례

### 현재 구현 확인

- 분석 대상: 공개 RFP 10개
- 추출 요구사항: 1,024개
- 빈 본문: 0개
- 중복 UID: 0개

이 수치는 현재 Markdown 변환본과 추출기 기준이며, 원본 PDF·HWP·HWPX 대조 전 최종 확정 수치로 사용하지 않는다.

### 논문 반영 위치

- 데이터 수집 및 전처리
- 데이터 품질 관리
- 재현성

## 4. 불릿과 텍스트 구조 전처리

### 결정

원문은 보존하고 모델 입력 생성 단계에서 불릿을 정규화한다.

```text
raw_text
→ normalized-list
→ 필요 시 flat 비교본
```

기본 입력은 `normalized-list`로 한다.

- `◦`, `○`, `●`, `•`, `▪`, `■`, `□` 등 줄 시작 불릿을 `-`로 통일한다.
- 목록의 줄 경계는 유지한다.
- `AI-플랫폼`, `1-2년`, 요구사항 ID 등 본문 내부 하이픈은 보존한다.
- 숫자, 금액, 기간, 비율, 영문 약어는 삭제하지 않는다.
- 원문 단어를 요약하거나 다시 쓰지 않는다.

### 근거

문서 구조를 보존하는 태그와 계층 정보를 활용했을 때 문서 분류 또는 독해 성능이 향상된 선행연구가 있다. 반면 RFP마다 다른 불릿 문자를 그대로 사용하면 문자 기반 모델이 문서 또는 기관의 서식 차이를 학습할 수 있다. 따라서 불릿의 종류는 통일하되 목록 경계는 보존한다.

직접적으로 “RFP 불릿 유지 대 제거”를 검증한 선행연구는 확인하지 못했다. 따라서 불릿 정규화의 효과는 선행연구의 확정 결론이 아니라 본 연구 데이터에 적합한 설계 가설이다.

### 현재 구현 확인

- 10개 문서에서 문서당 2개, 총 20개 요구사항 표본 생성
- 원본 용량이 가장 큰 `국방 지능형 플랫폼 고도화 구축` RFP 전체 169개 요구사항 처리
- 해당 문서에서 불릿 정규화가 발생한 행: 161개
- 줄 시작 미처리 특수 불릿: 0개
- 빈 전처리 결과: 0개

### 발견된 한계

PDF·HWP 변환 과정에서 중첩 표의 셀 경계가 붙을 수 있다. 예를 들어 표가 다음처럼 평탄화될 수 있다.

```text
연번기능용도수량
1WEBWEB 서버12
```

이는 불릿 정규화 문제가 아니라 원문 변환 및 표 추출 문제다. 표 셀 경계 보존 규칙과 원본 대조가 별도로 필요하다.

### 관련 선행연구

- Maillette de Buy Wenniger et al. (2020), *Structure-Tags Improve Text Classification for Scholarly Document Quality Prediction*
- Wan et al. (2021), *Does Structure Matter? Encoding Documents for Machine Reading Comprehension*
- Camacho-Collados and Pilehvar (2017), *On the Role of Text Preprocessing in Neural Network Architectures*
- Karimi et al. (2021), *AEDA: An Easier Data Augmentation Technique for Text Classification*

### 논문 반영 위치

- 선행연구: 문서 구조와 전처리
- 연구 방법: 텍스트 정규화
- 실험 또는 부록: `raw`, `normalized-list`, `flat` 생성 규칙

## 5. 모델 입력에 요구사항명 포함

### 결정

모든 학습·임베딩·파인튜닝 입력에 요구사항명과 본문을 함께 사용한다.

```text
요구사항명: {requirement_name}

요구사항 내용:
{preprocessed_text}
```

`raw_text` 자체에 요구사항명을 덧붙이지 않는다. 모델 입력을 생성할 때만 결합한다.

### 근거

요구사항명은 발주기관이 제공한 원문 정보이며 본문의 핵심 주제를 압축한다. 실제 예측 시점에도 사용할 수 있으므로 데이터 누수가 아니다. 연구 범위를 과도하게 늘리지 않기 위해 본문 단독 입력과의 별도 비교 실험은 현재 수행하지 않는다.

### 논문 반영 위치

- 모델 입력 구성
- 데이터 누수 방지 설명

## 6. 위험 분류와 전체 문서 검토의 분리

### 결정

실제 워크플로우를 두 단계로 분리한다.

```text
1단계: 요구사항 단위 국소 위험 분류
→ 2단계: 전체 RFP 문맥을 이용한 검토 및 조정
```

### 1단계: 본 연구의 학습·분류 범위

입력:

```text
요구사항명 + 해당 요구사항 본문
```

출력 후보:

- 통상수용
- 견적반영
- 계약·질의검토

요구사항만으로 알 수 없는 인프라 제공 여부, 전체 일정, 예산, 공통 계약조건은 추측하지 않는다. 필요한 경우 판단 근거에 `정보 부족` 또는 `전체 문서 확인 필요`를 기록한다.

### 2단계: 후속 검토 워크플로우

1단계에서 선별된 위험 후보를 중심으로 전체 RFP에서 다음 문맥을 확인한다.

- 발주기관 제공 인프라와 데이터
- 전체 사업기간과 단계별 일정
- 예산과 수량
- 공통 검수·성능 조건
- 무상지원, 유지보수와 책임 범위
- 다른 요구사항에 기재된 예외와 완화 조건

확인 결과에 따라 1단계 위험을 완화하거나 상향할 수 있다.

### 예시

```text
요구사항 단독: GPU 서버 구축 → 견적반영
전체 문서 확인: GPU 서버를 발주기관이 제공 → 위험 완화 가능
```

```text
요구사항 단독: 일반 성능시험 → 통상수용
전체 문서 확인: 검수 기준 불명확, 실패 시 무상 재수행 → 계약·질의검토로 상향 가능
```

### 연구 타당성 규칙

LLM 라벨러와 후속 학습 모델은 같은 정보를 봐야 한다. 요구사항 단위 모델을 학습할 때 LLM 라벨러에게 전체 RFP 문맥을 제공하지 않는다. 전체 문서를 보고 만든 라벨을 요구사항 본문만 보는 모델에 학습시키면 입력 정보가 불일치하고 라벨을 재현할 수 없기 때문이다.

### 논문용 범위 문장

> 본 연구는 개별 요구사항에 명시된 국소적 위험을 분류하며, 문서 전역의 조건에 따른 최종 위험 조정은 후속 검토 단계로 분리한다.

### 논문 반영 위치

- 연구 문제와 적용 범위
- 라벨링 프로토콜
- 실제 활용 워크플로우
- 연구 한계와 후속 연구

## 7. 현재 확정하지 않은 항목

다음 내용은 데이터 감사와 라벨링 파일럿 이후 결정한다.

- 세 주 라벨의 최종 경계
- `정보 부족`을 독립 라벨로 둘지 보조 필드로 둘지
- 사람 감사 표본 크기
- 중첩 표를 모델 입력에서 어떤 문자열 형식으로 표현할지
- 긴 요구사항의 최대 토큰 처리 방식
- 전체 RFP 문맥 검토를 후속 데모에 어느 수준까지 구현할지
