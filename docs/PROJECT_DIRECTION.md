# RFP 요구사항 견적·계약 검토 ML 프로젝트

> 상태: 초기 연구 설계안  
> 기준일: 2026-08-12  
> 범위: `RFP_data/`의 한국 공공 AI·IT 구축 RFP 10개

> **문서 역할:** 연구 목적, 가설, 전체 실험 설계와 로드맵을 설명하는 설계도다.  
> **권위 수준:** 프로젝트의 장기 목적과 범위를 정의한다. 상세 의사결정 근거는 [`history/`](history/)에 시간순으로 보존한다.
> **수정 시점:** 연구 질문, 범위, 비교 모델, 평가 계획 또는 전체 실행 순서가 바뀔 때 수정한다.

## 1. 프로젝트 정의

서로 다른 AI 구축 RFP에서 요구사항을 정확히 추출하고, LLM으로 실무 조치 라벨을 생성한 뒤 전통 ML·임베딩 기반 ML·경량 언어모델 파인튜닝 성능을 비교한다.

최종 사용자는 AI·IT를 이해하지만 산업별 전문가는 아닌 제안서 작성자다. 모델은 객관적인 손실확률을 예측하지 않는다. 요구사항을 다음 세 조치 중 하나로 분류해 견적 누락과 계약상 위험을 먼저 검토하도록 돕는다.

- 통상수용
- 견적반영
- 계약·질의검토

이 프로젝트는 하나의 실험을 세 용도로 연결한다.

- 실무: 제안서 작성자가 먼저 검토할 요구사항을 좁힘
- 포트폴리오: 문서 전처리, EDA, LLM 라벨링, 전통 ML, 파인튜닝과 오류 분석 역량을 보여줌
- 연구: 앵커링이 LLM 라벨의 일관성과 후속 ML 성능을 개선하는지 검증

현재 중심은 데이터 분석·전처리·ML 비교·파인튜닝이다. 완전한 RAG 서비스, AI Agent와 LLMOps는 핵심 연구 이후의 확장으로 둔다.

## 2. 현재 결정과 제약

### 2.1 합의된 방향

- 현재 공개 RFP 10개에서 요구사항 데이터를 새로 추출한다.
- 데이터와 모델 입출력의 논리적 단위는 요구사항 하나다.
- 기준 사용자는 공공 AI·IT 구축사의 제안서 작성자다.
- 주 타깃은 추상적인 위험도가 아니라 실무 검토 조치다.
- 도메인 의존성은 주 라벨과 분리된 보조 축으로 본다.
- LLM 라벨링 자체를 연구 대상으로 삼는다.
- 앵커 풀은 실험 전에 동결하고, 입력별로 관련 앵커만 동적으로 선택한다.
- 문서 단위 데이터 분할로 처음 보는 기관과 도메인에 대한 일반화를 평가한다.
- 딥러닝 비교 실험은 PyTorch를 사용해 구현하고, 학습·평가·체크포인트 관리 과정을 포트폴리오에 드러낸다.

### 2.2 작업 가설

- 주 라벨은 `통상수용 / 견적반영 / 계약·질의검토` 3개가 적절하다.
- 고정 루브릭과 동적 few-shot을 함께 쓰면 zero-shot보다 판정이 안정될 수 있다.
- 위험 요인을 먼저 분해한 뒤 주 라벨을 산출하면 직접 3분류보다 일관성이 높아질 수 있다.
- 문자·단어 TF-IDF와 선형 모델은 소량의 한국어 RFP 데이터에서 강한 기준선이 될 수 있다.
- 경량 인코더 파인튜닝은 충분한 품질의 silver label이 확보됐을 때만 의미 있는 이득을 낼 수 있다.

### 2.3 제약

| 제약 | 설계에 미치는 영향 |
|---|---|
| 품질이 속도보다 우선 | 전체 라벨링 전에 추출 감사와 소규모 파일럿 수행 |
| GPU 예산 약 5천 원 | 전통 ML과 고정 임베딩을 먼저 하고 경량 모델만 제한적으로 파인튜닝 |
| 공개 RFP 10개 | 문서 단위 평가와 과적합·도메인 혼입 분석 필수 |
| 수동 라벨링 최소화 | 사람 검토는 대표 표본, 경계 사례와 앵커 후보에 집중 |
| 실제 입력은 요구사항 단위 | 세부 불릿을 독립 학습 행으로 만들지 않음 |
| 포트폴리오·논문 공개 | 출처, 원문 위치와 실행 조건을 추적 가능하게 보존 |

## 4. 기준 사용자와 적용 범위

### 4.1 기준 사용자

식별자: `persona_ai_it_proposal_writer_v1`

1차 사용자는 AI 솔루션 기업, IT 서비스 기업 또는 SI 사업자에서 공공 RFP를 검토하고 제안 범위와 견적을 작성하는 실무자다.

사용자가 안다고 가정하는 것:

- 일반적인 소프트웨어 구축 절차와 공공 SI 용어
- 서버, 네트워크, DB, API, 시스템 연계, 클라우드와 온프레미스의 기본 구조
- LLM, RAG, 파인튜닝, 임베딩, 프롬프트와 모델 서빙의 기본 개념
- 인력, 기간, 라이선스, 장비, 테스트와 유지보수의 견적 요소
- 보안·개인정보·품질 요구가 추가 작업을 만든다는 사실

기본 보유를 가정하지 않는 전문성:

- 의약품 심사·인허가와 규제과학
- 국방 보안, K-RMF와 군 체계 인증
- 금융 규제, 신용평가·채무조정과 금융 컴플라이언스
- 도박중독·중독행동 분석과 임상적 판정
- 각 발주기관의 내부 업무 규정과 고유 데이터 구조
- 법률 분쟁, 회계와 원가에 대한 최종 판단

이 페르소나 문구는 LLM 프롬프트, 앵커 메타데이터, 사람 감사 지침과 오류 분석에서 동일하게 사용한다.

### 4.2 모델이 돕는 일

- 요구사항별 검토 조치 후보 분류
- 비용·책임·범위·검수·도메인 의존성 근거 표시
- 먼저 읽어야 할 요구사항 선별
- 누락하기 쉬운 비용과 발주처 질의 항목 제시

### 4.3 모델이 대신하지 않는 일

- 최종 견적금액 산출
- 입찰 참여 여부 자동 결정
- 법률 자문이나 계약 조항의 유·무효 판단
- 특정 기술의 실제 성능 보증
- 문서에 없는 사실 추정
- 산업 전문가의 최종 판정

현재 적용 범위는 한국 공공부문의 AI·IT 구축 RFP다. 다른 산업, 순수 연구용역, 건설, 제조 설비와 일반 물품구매까지 일반화하지 않는다.

## 5. 문제 정의와 라벨

### 5.1 핵심 질문

> 이 요구사항을 그대로 수용한 상태에서 믿을 만한 금액과 수행 범위를 산정할 수 있는가?

### 5.2 주 라벨 초안

| 라벨 | 의미 | 대표 상황 |
|---|---|---|
| `통상수용` | 별도 견적 또는 계약 질의 없이 일반적으로 이행 가능 | 일반 보고, 표준 산출물, 통상적인 테스트 |
| `견적반영` | 부담은 있으나 범위·수량·책임을 계산할 수 있음 | 명시된 상주인력, 교육 횟수, 연계 수, 보증기간 |
| `계약·질의검토` | 범위나 책임이 열려 있거나 산정 근거가 부족함 | 무상 추가개발, 포괄 책임, 불명확한 검수·성능 기준 |

세 라벨에는 대략적인 순서가 있지만 객관적 위험확률이나 손실금액은 아니다. 정확한 의미는 `견적·계약 검토 우선도`다. 최종 경계는 요구사항 EDA와 파일럿 후 확정한다.

### 5.3 흔한 조항과 위험의 구분

업계에서 자주 수용되는 조항이라고 해서 비용이나 책임이 사라지지는 않는다.

- 부담이 크지만 계산 가능하면 `견적반영`이다.
- 흔한 조항이어도 범위가 열려 있으면 `계약·질의검토`가 될 수 있다.
- 조항의 빈도는 참고 정보이지 자동 하향 규칙이 아니다.
- 자주 수용됨, 협상 가능성이 낮음, 위험이 작음은 서로 다른 사실이다.

`계약·질의검토`는 거절하라는 뜻이 아니다. 발주처 질의, 제안 가정·제외사항 명시, 비용·예비비 반영, 내부 법무 검토 또는 잔여 책임 기록이 먼저 필요하다는 뜻이다.

## 6. 데이터 추출과 입력 설계

### 6.1 데이터 단위

```text
요구사항 ID 하나 = 데이터 행 하나 = 예측 결과 하나
```

세부 불릿은 독립 학습 행으로 분해하지 않는다. 같은 요구사항 안의 조건, 예외, 제공 주체와 책임 범위를 함께 읽어야 하기 때문이다. 긴 요구사항은 행을 쪼개지 않고 모델 내부에서 여러 구간을 읽고 통합하는 방식을 검토한다.

### 6.2 결정론적 추출 원칙

- LLM이 요구사항을 요약하거나 다시 쓰지 않게 한다.
- `raw_requirement_text`에 원문을 그대로 보존한다.
- 정규화 본문은 별도 필드로 둔다.
- 문서·페이지·표·행·절 등 원문 위치를 기록한다.
- 문서별 형식 차이는 어댑터 또는 명시적 규칙으로 처리한다.
- 안정적인 `requirement_uid`를 생성하고 중복·누락을 검사한다.
- 목록의 요구사항 ID와 상세표가 1:1로 대응하는지 감사한다.
- 추출 규칙과 데이터셋 버전을 실행 기록에 남긴다.

### 6.3 입력 스키마 초안

```json
{
  "document_id": "...",
  "agency": "...",
  "domain": "...",
  "requirement_uid": "...",
  "requirement_id": "ECR-001",
  "requirement_type": "시스템 장비 구성",
  "requirement_name": "인프라 구축",
  "raw_requirement_text": "요구사항 세부내용 전체",
  "normalized_requirement_text": "...",
  "section_title": "...",
  "source_location": "..."
}
```

RFP에 적힌 요구사항 유형은 예측 타깃이 아니라 입력 메타데이터와 EDA에만 사용한다.

## 7. 위험 판단 구조

### 7.1 보조 위험 요소

주 라벨 하나만으로 이유를 설명하기 어려우므로 LLM은 다음 요소를 함께 생성할 수 있다.

- 본질적 부담: 요구 자체의 규모와 난이도
- 비용 요인: 인력, 장비, 라이선스, 외부 전문기관, 운영과 유지보수
- 범위 요인: 수량·기간·대상·완료조건의 상한
- 책임 요인: 수행사 책임, 무상 범위, 손해배상과 제3자 책임
- 검수 요인: 성능 기준, 정답 정의, 평가 데이터와 합격 조건
- 완화 조건: 발주기관 제공 자원, 충분한 기간과 명확한 범위
- 가중 조건: 포괄 책임, 추가 비용 불인정, 변경 가능성과 불명확한 기준
- 정보 부족: 현재 요구사항만으로 확인할 수 없는 항목
- 판단 근거: 라벨에 직접 영향을 준 원문 구간

파인튜닝의 최초 주 타깃은 `action` 하나로 단순하게 유지한다. 보조 요소는 라벨 감사, EDA와 오류 분석에 먼저 사용한다.

### 7.2 도메인 의존성

도메인 난이도는 계약 독소성이나 비용 위험과 같은 개념이 아니다. `domain_dependency`를 주 라벨과 분리된 보조 축으로 둔다.

```json
{
  "domain_dependency": "높음",
  "required_domain": "채무조정 제도",
  "domain_support": "부분 제공",
  "domain_responsibility": "공동",
  "domain_gap_reason": "추천 정답과 검증 기준의 업무부서 확정 필요"
}
```

판단 원칙:

> 도메인 격차 × 발주기관 지원 × 수행사 책임을 함께 보고 최종 조치를 정한다.

- 전문지식이 필요해도 발주기관이 데이터·규칙·검증을 제공하면 `견적반영`일 수 있다.
- 전문지식과 함께 정답, 데이터, 검수 기준과 책임 주체가 불명확하면 `계약·질의검토` 가능성이 커진다.
- 기술적으로 어려워도 사양과 부담 범위가 명확하면 도메인 위험보다 `견적반영`에 가깝다.
- 포괄적인 저작권·손해배상 책임은 도메인 난이도와 별개의 계약 위험이다.

### 7.3 요구사항 밖의 문맥

일정, 전체 성능과 시스템 충돌은 여러 요구사항을 함께 봐야 드러날 수 있다. 장비 요구가 커도 다른 절에서 발주기관 제공을 명시할 수 있다.

초기 주 모델은 요구사항에 명시된 국소 위험을 다룬다. 문서 전체에서 관련 조건을 검색하는 기능은 별도 실험으로 둔다.

- 같은 문서 검색: 현재 요구사항의 제공 조건·예외·상한 확인
- 다른 학습 문서 검색: 유사한 라벨 사례와 앵커 찾기

문서에 필요한 정보가 없으면 사실을 추정하지 않고 `정보 부족` 또는 `발주처 확인 필요`로 표시한다.

## 8. LLM 라벨링과 앵커링

### 8.1 연구 질문

1. LLM이 검토 조치를 반복해서 일관되게 라벨링할 수 있는가?
2. 동적 few-shot은 zero-shot보다 동일·유사 요구사항의 판정을 안정시키는가?
3. 위험 요인 분해 후 라벨 산출이 직접 3분류보다 안정적인가?
4. 라벨링 전략의 차이가 후속 ML과 파인튜닝 성능으로 이어지는가?
5. 처음 보는 기관과 도메인에도 일반화되는가?

### 8.2 비교할 방식

- 고정 루브릭만 제공하는 zero-shot
- 모든 입력에 같은 예시를 주는 global few-shot
- 무작위 few-shot
- 유사 요구사항 기반 dynamic few-shot
- 유사성에 위험 요인·경계 사례 커버리지를 결합한 dynamic few-shot
- 위험 요인 분해 후 고정 규칙으로 주 라벨 산출

LLM, temperature, 출력 스키마, 입력 순서와 실행 조건은 기록하고 가능한 한 고정한다.

### 8.3 앵커링 원칙

앵커링의 주 목적은 같은 요구사항을 실행할 때마다 다르게 판단하는 문제를 줄이는 것이다. 일관성과 타당성은 별도로 평가한다. 같은 오답을 반복하는 모델도 일관성은 높을 수 있다.

고정할 것:

- 기준 사용자
- 주 라벨 정의와 판단 순서
- 문서에 없는 사실을 추측하지 않는 원칙
- 출력 JSON 스키마
- 실험 중 사용하는 앵커 풀 버전

동적으로 바꿀 것:

- 각 입력 프롬프트에 넣을 관련 사례

> 동적 앵커는 동결된 풀에서 입력별 사례를 선택하는 방식이다. 실행 중 새 LLM 출력을 풀에 추가하지 않는다.

앵커 풀은 대표 사례, 경계 사례와 라벨링 방식 간 불일치 사례를 후보로 모은 뒤 소규모 사람 감사를 거쳐 동결한다. 각 앵커에는 원문 전체, 출처, 페르소나 버전, 라벨, 판단 요소, 이유, 검토 상태와 풀 버전을 기록한다.

### 8.4 앵커 선택과 누수 방지

- 텍스트 유사성을 우선한다.
- 비슷한 사례가 많으면 위험 요인과 문서·도메인 다양성을 보완한다.
- 라벨 균형을 맞추려고 무관한 사례를 억지로 넣지 않는다.
- BM25, 임베딩, MMR 같은 단순 검색·다양화 방식을 먼저 비교한다.
- 평가 fold의 라벨은 앵커 풀 구축에 사용하지 않는다.
- fold마다 학습 문서만으로 앵커 풀 또는 사용 가능한 앵커 집합을 구성한다.

유사 문구라도 제공 주체, 비용 부담, 상한, 데이터 제공, 검수 기준과 책임 범위가 다르면 라벨이 달라질 수 있다. 차이는 반드시 근거 필드로 설명돼야 한다.

## 9. ML 실험 설계

### 9.1 전체 흐름

```text
요구사항 추출·무결성 검사·EDA
  -> LLM 라벨링 전략 비교
  -> TF-IDF 기반 전통 ML
  -> 고정 임베딩 + ML
  -> 경량 언어모델 파인튜닝
  -> 문서·도메인 단위 평가와 오류 분석
```

### 9.2 기준선과 비교 모델

- 최저 기준: DummyClassifier
- 주 기준선: 문자 3~4gram TF-IDF + balanced Logistic Regression
- 표현 비교: 단어 1~2gram, 문자+단어 결합 TF-IDF
- 강한 선형 비교: 같은 문자 TF-IDF + Linear SVM
- 추가 비교: Complement Naive Bayes 완료, 순서형 분류는 필요 시 검토
- 의미 표현 비교: 사전학습 문장 임베딩 + Logistic Regression/SVM
- 최종 비교: 경량 한국어 인코더 파인튜닝

한국어 RFP에는 띄어쓰기 변형, 기관별 용어, 영문 코드와 약어가 많으므로 문자 n-gram을 반드시 포함한다.

### 9.3 통제 비교

| 비교 | 고정 | 변경 | 확인할 것 |
|---|---|---|---|
| zero-shot vs dynamic few-shot | 모델·입력·분할 | 학습 라벨 생성 전략 | 앵커링의 downstream 효과 |
| Logistic vs SVM | 라벨·특징·분할 | 분류기 | 선형 모델 차이 |
| TF-IDF vs 임베딩 | 라벨·분할 | 표현 방식 | 사전학습 의미 표현의 효과 |
| 임베딩 ML vs 파인튜닝 | 라벨·분할 | 인코더 학습 여부 | 제한된 GPU 비용 대비 추가 이득 |

### 9.4 PyTorch 구현과 모델 저장

딥러닝 비교 실험에는 PyTorch를 명시적으로 사용한다. Hugging Face Transformers의 사전학습 인코더를 활용할 수 있지만, 포트폴리오에서 구현 역량을 확인할 수 있도록 최소한 다음 요소를 직접 구성하고 기록한다.

- `Dataset`과 `DataLoader`
- 학습·검증 루프
- optimizer와 learning-rate scheduler
- class weight 또는 weighted loss
- early stopping과 best-checkpoint 선택
- seed와 실행 환경 고정

추론용 최종 가중치는 `state_dict` 또는 `safetensors` 형식으로 저장한다. 중단 후 학습 재개가 필요한 체크포인트에는 모델뿐 아니라 optimizer, scheduler, epoch, 설정 버전과 라벨 매핑도 함께 보존한다. 모델 바이너리는 Git에 직접 커밋하지 않는다.

### 9.5 실험 및 아티팩트 관리

초기 실험 추적 도구는 오픈소스 MLflow를 우선 검토한다. 로컬 환경에서 시작해 실행별로 다음 항목을 연결한다.

- 모델명, 데이터셋·라벨·분할 버전
- learning rate, batch size, epoch, class weight와 seed
- train/validation loss, Macro F1과 `계약·질의검토` Recall
- best epoch와 PyTorch 체크포인트
- confusion matrix, 예측 결과와 오류 분석 자료

사람이 정하는 앵커 선택 가중치와 학습 설정은 YAML로 저장해 Git으로 버전 관리한다. 학습으로 생성되는 모델 가중치와 실행 산출물은 MLflow artifact로 관리한다. 데이터와 대용량 모델 파일을 원격 저장소와 함께 버전 관리할 필요가 생기면 DVC를 추가하되, 초기에는 MLflow와 역할을 중복시키지 않는다.

## 10. 평가 설계

### 10.1 분할 — 확정 (2026-08-23)

행 무작위 분할을 주 평가로 사용하지 않는다. 기관이 달라도 보안, 품질과 유지보수 문구가 반복돼 누수가 생길 수 있다.

**문서 단위 leave-one-document-out 10겹**을 쓴다. fold마다 셋으로 가른다.

```
학습 8문서 / 검증 1문서 / 평가 1문서
```

- 모든 문서가 정확히 한 번씩 평가 문서가 된다. §8.1의 다섯 번째 연구질문에 직접 답한다
- 검증 문서는 회전으로 정한다(fold `i`의 평가가 `docs[i]`이면 검증은 `docs[i+1]`).
  파인튜닝의 early stopping은 평가 문서를 보고 고를 수 없고(§9.4), 한 문서를 고정하면
  그 난이도가 모든 fold의 조기 종료 시점에 같은 방향으로 스며든다
- **모든 모델이 같은 8문서로 학습한다.** early stopping이 필요 없는 모델도 마찬가지다.
  §9.3의 통제 비교는 분할을 고정하고 모델만 바꾸는 것이라, 학습량이 다르면 결과 차이에
  학습량 차이가 섞인다
- fold별로 기준선 **둘**을 병기한다 — 학습 최빈을 찍는 Dummy(배포 가능)와 평가 문서 안의
  최빈 비율(oracle, 난이도 눈금). 앵커 제외 후 2개 fold에서 두 값이 갈린다
- 집계는 fold 단순 평균과 건수 가중을 **둘 다** 낸다(issues/003)
- fold별 반복 문구 노출률을 함께 적고, 점수를 전체 / 반복 제외 / 반복만으로 낸다(issues/006)
- 평가 문서 라벨의 앵커 사용 금지. 동결 앵커 100건은 검증·평가에서도 제외하므로
  데이터셋 1,024건 중 평가 합계는 924건이다(결정 25)

구현은 `scripts/evaluation/folds.py`이고 `python -m scripts.evaluation.folds`로 fold 표를
출력한다. 근거는 `history/decisions-04.md`.

### 10.2 지표

- Macro F1
- 클래스별 Precision, Recall과 F1
- `계약·질의검토` Recall
- 검토 대상 누락률
- 상위 N개 검토 시 주요 조항 포착률
- Weighted Cohen's Kappa
- 동일 입력 반복 라벨 일치율
- 입력 순서·seed·앵커 변화에 대한 민감도
- 유사 요구사항의 조건부 라벨 일관성

Accuracy는 클래스 불균형 때문에 보조 지표로만 사용한다.

### 10.3 사람 감사

전체 수동 라벨링 대신 두 표본을 분리해 검토한다.

- 대표 표본: 문서·라벨 후보·요구사항 유형을 고려한 무작위 또는 층화 표본
- 도전 표본: 불확실, 충돌, 경계, 도메인 의존성이 높은 사례

대표 표본은 전체 품질 추정, 도전 표본은 실패 원인 분석에 사용하며 결과를 따로 보고한다. 가능하면 일부를 두 명이 독립 검토한다. 한 명만 가능하면 일정 후 재판정해 자기 일관성을 측정하고 한계로 밝힌다. 검토자는 LLM 라벨과 이유를 보기 전에 먼저 판정한다.

## 11. 예상 리스크와 대응

### 11.1 문서별 형식 차이

같은 RFP라도 표 병합, 목록과 상세표, 요구사항 ID 위치가 다르다. 공통 정규식 하나로 처리하면 누락·중복이 발생할 수 있다.

대응: 문서 구조 프로파일 작성, 문서별 어댑터, 목록-상세표 대조, 원문 위치 저장과 수동 감사 표본.

### 11.2 원문 변환 손실

PDF·HWP·HWPX를 Markdown으로 변환할 때 표 셀, 각주, 병합 구조, 부정문과 제공 주체가 손실될 수 있다.

대응: 원본과 Markdown 대응 검사, 원문 텍스트 별도 보존, 변환 오류 플래그와 출처 위치 기록.

### 11.3 요구사항 식별자 오류

동일 ID 반복, 표 제목 오인, 여러 요구의 합쳐짐 또는 하나의 요구가 중복 추출될 수 있다.

대응: 안정적 UID, 문서 내부 중복 ID 검사, 본문 유사도 검사, 목록과 상세표의 개수·대응 관계 감사.

### 11.4 LLM 라벨의 정답성

LLM 라벨은 실제 원가 초과, 변경계약, 분쟁과 납기 지연의 정답이 아니다. 후속 모델이 높은 성능을 내도 LLM 판단을 잘 모방한 것일 수 있다.

대응: 결과를 검토 조치 예측으로 제한해 표현하고, 사람 감사 표본과 실제 사례를 확보할 수 있을 때 외적 타당성을 별도 검증.

### 11.5 일관성과 타당성의 차이

앵커링이 반복 출력을 안정시켜도 잘못된 기준을 더 일관되게 재현할 수 있다.

대응: 반복 일치율과 사람 일치도를 분리해 보고하고, 앵커 후보를 감사하며, 오류 유형별 분석 수행.

### 11.6 한 요구사항의 여러 위험

하나의 요구사항에 비용, 보안, 검수와 책임 문제가 동시에 들어갈 수 있다. 단일 라벨은 이유를 잃는다.

대응: 주 조치는 하나로 유지하되 위험 요인과 근거를 다중 보조 필드로 저장.

### 11.7 요구사항 밖의 조건

사업기간, 데이터 제공 시점, 발주기관 제공 장비와 다른 절의 예외가 현재 요구사항의 의미를 바꿀 수 있다.

대응: 초기 모델의 한계를 명시하고 정보 부족을 표시. 문서 내 관련 조건 검색을 분리된 실험으로 평가.

### 11.8 라벨러와 학습 모델의 입력 불일치

LLM 라벨러가 문서 전체 문맥을 보지만 학습 모델은 요구사항만 보면 재현 불가능한 라벨이 생긴다.

대응: 각 실험에서 라벨러와 모델이 본 정보를 기록하고, 요구사항 단독 라벨과 문맥 보강 라벨을 섞지 않음.

### 11.9 클래스 불균형

`계약·질의검토`가 희소하면 Accuracy가 높아도 중요한 조항을 놓칠 수 있다.

대응: Macro F1과 해당 클래스 Recall 우선, class weight, 층화 감사와 threshold 분석. 목표 분포를 미리 정해 라벨을 강제로 맞추지 않음.

### 11.10 페르소나 의존성

같은 요구사항도 회사의 기술·도메인 역량에 따라 판단이 달라진다.

대응: 페르소나 버전 고정, 모든 프롬프트와 감사 지침에 같은 정의 사용, 일반화 범위 제한.

### 11.11 유사 문구와 다른 조건

거의 같은 문구라도 제공 주체, 무상 범위, 수량 상한과 책임 범위가 다르면 라벨이 달라야 한다.

대응: 단순 문장 유사도 외에 조건 서명과 근거 비교. 다른 라벨이면 설명 가능한 차이를 요구.

### 11.12 검색·앵커 오류

유사하지만 판단 요소가 다른 사례가 앵커로 선택되면 오히려 라벨이 왜곡될 수 있다.

대응: 검색 관련성 평가, top-k·MMR·위험 요인 보강 비교, 무관련 앵커 제외와 앵커 perturbation 테스트.

### 11.13 앵커 풀 오염과 경로 의존성

감사되지 않은 LLM 출력을 다시 예시로 쓰면 초기 오류가 확산되고 입력 순서에 따라 결과가 달라질 수 있다.

대응: 감사·버전 관리된 앵커 풀만 사용, 실행 중 풀 변경 금지, 순서 변경 반복 실험.

### 11.14 문서·도메인 혼입

RFP가 10개뿐이라 특정 기관 표현을 라벨 신호로 외울 수 있다.

대응: 문서 단위 분할, 기관명 마스킹 실험, 문서·도메인별 오류 보고와 유사 문구 누수 검사.

### 11.15 LLM 실행 환경 변화

API 모델 버전과 제공자의 업데이트로 같은 프롬프트 결과가 달라질 수 있다.

대응: 모델명·버전·temperature·프롬프트·seed·실행일·원본 응답과 run manifest 보존.

### 11.16 파인튜닝 과적합과 GPU 비용

소량 silver label에서는 큰 모델이 쉽게 문서 표현을 외우며, 제한된 예산 안에서 반복 실험도 어렵다.

대응: 전통 ML 우선, 작은 모델·짧은 epoch·early stopping·parameter-efficient tuning, 동일 split에서 비용 대비 이득 보고.

### 11.17 법률·사업 의사결정 오해

사용자가 분류를 법률 판정, 확정 견적 또는 입찰 결정으로 오해할 수 있다.

대응: 결과를 검토 우선순위와 근거로만 표시하고 최종 판단은 담당자에게 남김.

### 13.7 ML 비교 실험 — 진행 중

Dummy → TF-IDF 선형 → 임베딩 ML → 경량 인코더 순. **동결 문장 임베딩 ML까지 완료**
(2026-08-25). 기본 설정은 문자 3~4gram + `class_weight="balanced"` Logistic이고 LODO
fold 평균 macro F1 0.601이다(Dummy 0.219). 같은 분할에서 동결 `multilingual-e5-small`
384차원 입력은 Logistic 0.544, LinearSVC 0.546이었다. 동결 앵커 100건을 제외해 각
문서의 비앵커 요구사항 총 924건만 검증·평가한다.

측정으로 정한 것 둘.

- `class_weight`가 지금까지 만진 것 중 가장 큰 효과다(평균 +0.080, 9/10 fold 우세)
- 학습 문서 8 → 9는 잡음이다(평균 +0.001, 방향 불일정). 13.6의 8문서 통일을 뒷받침한다

`word → char`는 평균 +0.020에 편차 폭 0.205로 **판정을 보류했다.** §9.2가 문자 n-gram을
"반드시 포함"으로 둔 근거가 이 데이터에서는 그만큼 강하지 않다. 방향은 일정하므로
표본이 늘면 달라질 수 있어 단정하지 않고 기록만 남긴다.

검증 문서에서 계약 F2로 검토 클래스 가중치 `1.0 / 1.25 / 1.5 / 2.0배`를 선택한
LinearSVC도 macro F1 0.576, 계약 recall 0.509로 기준선을 넘지 못했다.

E5 Logistic은 TF-IDF Logistic보다 macro F1이 평균 0.057, 계약 recall이 0.071 낮았고
macro F1이 오른 fold는 2/10뿐이었다. 따라서 고정 E5 의미 표현도 현재 기준선을 넘지
못했다. 인코더를 학습하는 파인튜닝과는 다른 결과다.

단어 1~2gram과 문자 3~4gram을 결합한 Logistic은 macro F1 0.603, 계약 recall 0.532로
평균은 가장 높았지만 문자 단독 대비 macro F1 차이가 +0.003(-0.050~+0.067), 우세 5/10이라
잡음이다. ComplementNB는 같은 결합 입력에서 macro F1 0.505, 계약 recall 0.351로 낮았다.
재현되는 이득이 없어 주 기준선은 더 단순한 문자 TF-IDF Logistic 0.601을 유지한다.

정규화한 요구사항 유형 one-hot을 추가하면 문자 모델은 macro F1 0.549(기준선 대비
-0.051, 우세 2/10), 단어+문자 모델은 0.558(해당 기준선 대비 -0.046, 우세 1/10)로
낮아졌다. 유형은 분석 메타데이터로만 유지하고 모델 입력에서는 제외한다.

유형 블록 가중치 `0 / 0.05 / 0.1 / 0.25 / 0.5 / 1.0`을 fold별 검증 문서에서 선택해도
문자+유형은 macro F1 0.589, 단어+문자+유형은 0.584로 각 본문 기준선보다 낮았다.
단일 검증 문서에서 고른 유형 효과가 다음 문서에 안정적으로 일반화되지 않았다.

문자 TF-IDF에 `log(1+글자 수)`, 숫자 유무, `log(1+숫자 개수)`를 통제 추가했다.
글자 수는 macro F1 0.571, 숫자 정보는 0.591, 전체 결합은 0.572로 모두 기준선 0.601보다
낮았다. 숫자 정보는 6/10 fold에서 소폭 올랐지만 평균 -0.009이고 문서별 큰 하락이 남았다.

구조·수치 결합에 Elastic-net을 적용하면 macro F1 0.471(기준선 대비 -0.129, 우세 0/10),
TF-IDF를 SVD 100차원으로 압축한 Logistic은 0.528(-0.072, 우세 1/10), 같은 입력의
XGBoost는 0.564(-0.037, 우세 3/10)이었다. XGBoost가 압축 손실 일부를 회복했지만 원래
희소 문자 TF-IDF 기준선을 넘지 못했다. 세 결과는 고정 초기 설정의 모델 구조 비교이며
하이퍼파라미터 선택과 분리해 해석한다.

문자 TF-IDF와 동결 E5를 결합하고 fold별 검증 문서에서 E5 블록 가중치
`0 / 0.05 / 0.1 / 0.25 / 0.5 / 1.0`을 선택하면 macro F1 0.611로 숫자상 최고였다.
문자 단독 대비 +0.010(-0.029~+0.045), 우세 5/10이므로 안정적 개선으로 확정하지 않고
유망 후보로 둔다. 같은 결합에 숫자 정보를 추가하면 0.594로 낮아져 제외한다.

파인튜닝 전 설명 가능한 전통 ML을 추가 탐색했다. 기존 8/1/1을 유지하고 평가 문서를
제외한 회전 검증 1문서에서 후보를 고르면, Logistic 27조합은 macro F1 0.581(기준선
대비 -0.020, 우세 4/10), NB-SVM 6조합은 0.532(-0.069, 우세 0/10), fastText 3조합은
0.352(-0.249, 우세 0/10)였다. 특히 fastText 계약 recall은 0.052였다. 검증 문서 하나의
선택 신호가 다음 문서로 안정적으로 이어지지 않았고 새 선형·subword 모델도 기준선을
대체하지 못했다.

한국어 UD 의존구문 6개 해석 단위(주어·목적어·수식어·절·접속·서술어)의 개수와 비율
12개를 문자 TF-IDF에 통제 추가하면 macro F1 0.539, 계약 recall 0.458이었다. 기준선
대비 평균 -0.062(-0.288~+0.050), 우세 3/10으로 문서 간 일반화가 악화됐다. 문장 구조는
문서별 작성 양식과 길이에 묶여 안정적인 위험 신호가 아니었다. feature 분산의 집단 η²
평균도 문서 0.134, 라벨 0.068로 문서 차이가 약 두 배여서 입력에서 제외한다.

macro F1 0.6 이상 후보 3개의 동일한 924건 OOF 확률을 보존하고 고정 결합을 비교했다.
동일 가중 soft voting은 macro F1 0.607로 최고 단일 후보 0.611을 넘지 못했다. 세 후보는
822/924건(89.0%)에서 합의했고 259건(28.0%)에서는 모두 틀려, 단순 평균이 복구할 오류가
적었다. 하나라도 `계약·질의검토`를 예측하면 검토로 올리는 규칙은 macro F1 0.611,
계약 precision/recall/F1 0.563/0.580/0.559였다. 이는 단일 후보의 0.598/0.508/0.542보다
recall을 높이고 precision을 낮추므로 주 모델 교체가 아니라 검토 누락 비용이 큰 운영
조건에서 쓰는 선택지로 둔다.

같은 OOF 예측을 요구사항 단위로 감사할 수 있도록 정적 설명 화면을 둔다. 문자 Logistic의
예측 클래스와 2위 클래스 사이에서 각 문자 n-gram이 만든 `TF-IDF × 계수 차이`를 원문
위치에 겹쳐 표시하고, 세 후보와 동일 가중 평균의 클래스 확률·투표 및 검토 우선 결과를
함께 보여준다. 이는 모델이 계산에 사용한 상관 신호이지 계약 위험의 인과 설명이 아니다.
E5 임베딩 차원은 사람이 읽을 수 없으므로 색칠 근거에서 제외한다. 현재 화면은 평가 누수
방지를 위해 기존 924건 OOF 감사에만 쓰고, 새 문장 추론은 최종 학습 범위 결정 뒤 분리한다.
같은 로컬 기여도를 요구사항별 JSON, 클래스·문구별 합계 CSV, 클래스별 PNG 문구
클라우드로도 내보낸다. 문자 조각은 원문에서 포함된 단어로 확장하되 이 병합은 사람이
읽기 위한 표시 변환이며 모델 입력이나 평가값을 바꾸지 않는다.

남은 것 — 학습 8문서 안의 더 비싼 inner LODO를 추가할지, 경량 인코더 파인튜닝으로

### 14.2 남아 있음

- **더 비싼 inner LODO를 추가할 것인가.** 기존 회전 검증 1문서에서 `C`, `min_df`,
  `ngram_range`를 고른 첫 탐색은 평가 누수 없이 완료했지만 고정 기준선보다 낮았다.
  학습 8문서 안의 inner LODO 8겹은 선택 분산을 줄일 수 있으나 계산량이 커지고,
  현재의 통제 비교보다 성능 최적화 쪽으로 연구 질문이 이동한다.
- **파인튜닝 타깃 범위.** 주 라벨 단일 vs 다중 헤드. §12가 "처음부터 다중 과제 파인튜닝"을
  제외 범위로 두고 있어 §12 수정 여부가 선결이다(13.7). 파인튜닝 착수 자체는 미뤘다.
- 긴 요구사항을 어떤 모델 입력 방식으로 처리할 것인가?
- 사람 감사 표본의 크기와 검토자 수는 얼마로 할 것인가?
- dynamic few-shot에서 유사성, 위험 요인과 다양성을 어떤 비율로 반영할 것인가?
  현재 층화 인출의 유사도 중앙값이 0.090이라 사실상 "유사 사례"가 아니다
  ([`issues/008`](issues/008-anchor-retrieval-similarity.md))
- 유사 사례의 라벨이 충돌하면 루브릭과 사례 중 무엇을 우선할 것인가?
- 문서 내 관련 조건 검색을 핵심 실험에 포함할 것인가?
- `계약·질의검토`와 별도의 `정보 부족` 상태가 필요한가?
- 어떤 경량 한국어 인코더가 예산과 성능의 균형에 적합한가? (GPU 예산 약 5천 원)
