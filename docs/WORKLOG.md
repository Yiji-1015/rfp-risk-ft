## 2026-08-19 · 라벨 재정의와 전수 라벨링

하루가 길었던 날. 스키마를 두 번 갈아엎고 전수 라벨링까지 끝냈다.

**스키마 재설계** (결정 16~21)

주 라벨을 **가격 산정 가능성**으로 재정의했다. 그 전에는 `계약·질의검토`가 80%로
쏠렸는데, 원인을 보니 라벨이 뒤섞여 있었다 — 그중 47%는 계약적 위험이 없고 그냥
기술적으로 범위가 큰 항목이었다. 위험도를 묻는 대신 **"이 요구사항에 값을 매길 수
있는가"**를 묻자 구분이 서기 시작했다.

동시에 도메인 난이도와 구축 난이도를 분리하고, blocker를 5종 분류로 세웠다.
`[표준 문구 보정]` 블록을 넣어 관행적 품질·호환 문구가 blocker로 잘못 잡히는 것을
15건 중 6건에서 **0건**으로 줄였다.

**앵커 풀 동결** (결정 22, 25, 26)

few-shot 예시로 쓸 100건을 뽑아 zero-shot으로 3회 반복 라벨링하고, **3회 만장일치한
81건**만 통과시켰다. 사람 검토가 끝이 없어 반복 일치를 자동 감사로 대신했다.

한때 Chunk 1 결과를 앵커에 되먹여 192건으로 늘렸다가 되돌렸다. 실행 순서가 결과를
바꾸고, 누적하면 종국에 전체가 앵커가 되어 fold 분리가 불가능해지기 때문이다.
**v2(100건)에서 동결**했다.

**전수 라벨링**

배치 API로 1,024건을 처리했다. 동기 실행의 50% 가격이고, 제출 후 컴퓨터를 꺼도 된다.

실측 비용은 앵커 스크리닝 약 2,300원, 전수 라벨링 약 7,500원, 재시도 약 40원.
건당 단가는 배치 약 8원이다.

**겪은 문제**: 생성 반복(degeneration)으로 일부가 실패했다. 한국어로 시작해 다른
언어로 이탈하거나, 닫는 괄호를 무한 반복해 JSON이 깨지거나, 영어 메타 독백이 섞였다.
실측 실패율은 배치 0.43%, 동기 3.3%였고 재시도하면 전부 통과했다.

## 2026-08-20 · 데이터셋 확정

**프롬프트 캐시 최적화** (결정 29)

고정 앵커를 쓸 때 앵커 블록을 캐시되는 system 블록으로 옮겼다. 캐시 브레이크포인트를
둘로 나눠 기본 프롬프트는 zero-shot 실행과도 캐시를 공유하게 했다.
전수 기준 배치 입력 비용이 **6,912원 → 2,619원**.

구현 도중 캐시가 전혀 안 붙는 문제를 만났다. 앵커에 붙는 "공통 어휘"가 대상마다
계산돼서 블록 텍스트가 매번 달라졌기 때문이다. 고정 앵커는 유사도로 뽑은 게 아니라
그 표기 자체가 사실과도 달랐으므로, 전용 헤더로 분리했다.

**전면 재실행 검토와 기각** (결정 30)

`산출정보` 열 누락을 고치려면 데이터셋 재생성 + 전수 재라벨링(약 9,000원)이 필요했다.
실측해보니 **얻는 게 35.5%뿐**이고 문서 편중이 심했다(신용회복위원회 95.8% ~ 3개 문서 0%).
문서와 상관된 특징을 새로 넣는 셈이라 기각했다.

**라벨 데이터셋 정리와 동결** (결정 31, 32)

- 고정 규칙 위반 **6건(0.6%)** 보정. `reasoning`을 전건 읽어보니 6건 모두 근거 문장이
  규칙 쪽을 지지했다. 한 건은 모델이 reasoning 안에서 스스로 정정해놓고 필드를
  안 고친 경우였다. 임의 덮어쓰기가 아니라 모델 자신의 근거와 맞추는 일이었다.
- 실행 결과 세 곳을 **균일 스키마**로 합치고 `execution_path`·`source_run`을 명시했다.
- 요구사항 유형 **60종 → 정본 12종**으로 정규화. 정규화하니 통상수용 비율이 단조롭게
  정렬됐다(시스템장비구성 1.3% → 프로젝트관리 76.2%). 흩어져 있을 때는 안 보이던 순서라,
  잡음을 지운 게 아니라 신호를 드러냈다고 본다.
- SHA-256 대조 로더로 **동결**. 파일이 조용히 바뀌면 분석이 실패한다.

**이슈 목록 신설** (결정 33, 34)

데이터 결함을 담을 자리가 없어 [`issues/`](issues/)를 만들고 8건을 정리했다.

정리하고 보니 목록이 실제 위험보다 커 보였다. 학습 입력을 **요구사항 원문으로 한정**한다는
전제를 밝히자 절반이 성격을 바꿨다. 실제로 학습에 영향을 주는 것은 004(라벨 품질)와
005(희소 값) 둘뿐이다.

두 건은 사용자 지적으로 진단을 내렸다.

- 문서별 건수·라벨 편차(003)를 결함으로 적었으나, **건수는 학습 입력이 아니고
  분포 차이는 사실이다.** 어떤 RFP는 정말 더 쉽다. 평가 보고 방식의 문제로 내렸다.
- 문서 간 문구 반복(006)을 "누수"로 적었으나, **중복도 누수도 아니다.** 서로 다른
  사업의 별개 요구사항이 표준 문구를 공유할 뿐이고, 배포에서도 같은 조항이 나오므로
  알아보고 답하면 그건 정답이다. 남는 건 점수가 두 능력을 섞는다는 것뿐이다.

관측은 옳았고 해석이 틀렸던 사례로 남겼다.

## 다음에 할 일

### 1. fold 분할 설계 — 바로 다음

모델을 평가하려면 데이터를 학습용과 시험용으로 나눠야 한다. **문서 단위로** 나눈다(§10.1).
무작위로 섞으면 같은 RFP의 비슷한 요구사항이 양쪽에 갈라져 들어가 누수가 된다.

문서가 10개뿐이라 정할 것이 있다.

- 8:2 한 번 vs 10겹 교차검증 (매번 1개씩 시험용)
- fold별 다수 클래스 기준선 병기 방식 (issues/003)
- 희소 값을 어느 fold에 배정할지 (issues/005 — `외부인증` 3건은 어디 넣든 한쪽이 0건)
- 표준 문구 반복 노출률 보고 방식 (issues/006)

### 2. ML 비교 — §9

```
DummyClassifier → TF-IDF + Logistic/SVM → 사전학습 임베딩 + ML → 경량 인코더 파인튜닝
```

각 단계는 "복잡하게 만든 값을 했는가"에 답한다. TF-IDF가 파인튜닝과 비슷하게 나오면
"이 문제엔 TF-IDF로 충분하다"가 결론이고, 그것도 유효한 결과다.

### 3. 선결 결정

- **파인튜닝 타깃 범위** — 주 라벨 하나만 vs 다중 헤드로 보조 축까지.
  §12가 "처음부터 다중 과제 파인튜닝"을 제외 범위로 두고 있어 §12 수정 여부가 먼저다.
- **어떤 경량 한국어 인코더** — §14의 열린 질문. GPU 예산 약 5천 원 제약이 있다.
