# 가이드 01 — 데이터셋은 어떻게 만들어졌고, 무엇을 봐야 하는가

> 학습용 요약본이다. 시간순 기록은 [`../history/`](../history/)와 [`../WORKLOG.md`](../WORKLOG.md)에,
> 실행 절차는 [`../PIPELINE.md`](../PIPELINE.md)에 있다. **숫자가 어긋나면 그쪽이 정본이다.**
>
> 이 문서는 "언제 정했나"가 아니라 **"왜 그렇게 하는가"**로 다시 엮은 것이다.

---

## 1. 데이터셋이 나오기까지 — 결정의 줄기

### 1-1. 무엇을 물을 것인가

처음에는 요구사항의 **위험도**를 물었다. 그랬더니 `계약·질의검토`가 80%로 쏠렸다.
원인을 뜯어보니 그중 **47%는 계약적 위험이 없고** 그냥 기술적으로 규모가 큰 항목이었다.
"위험"이라는 말에 서로 다른 두 가지가 섞여 있었던 것이다.

질문을 바꿨다.

> 이 요구사항을 그대로 수용한 상태에서 **믿을 만한 금액을 산정할 수 있는가?**

| 라벨 | 기준 |
|---|---|
| `통상수용` | 추가 원가 없음 |
| `견적반영` | 원가는 붙지만 원문 정보로 **계산 가능** |
| `계약·질의검토` | blocker가 있어 **계산 불가** |

**배울 점: 분류가 안 되면 모델을 바꾸기 전에 질문을 의심한다.** 라벨이 안 갈리는 건
모델 탓이 아니라 라벨 정의가 두 개념을 섞고 있어서일 때가 많다.

### 1-2. 어떻게 물을 것인가 — 분해하고 규칙으로 합치기

주 라벨을 바로 묻지 않는다. **보조 축 4개를 먼저 묻고 고정 규칙으로 주 라벨을 도출**한다.

```
blockers가 있으면              -> 계약·질의검토
없고 cost_basis != 없음이면    -> 견적반영
둘 다 아니면                   -> 통상수용
```

이걸 `derive_primary_action()`이 구현한다. 전수 1,024건에서 모델이 직접 낸 주 라벨과
규칙 도출 결과가 **99.4% 일치**했다.

**배울 점: 분해하면 검산이 생긴다.** 라벨 하나만 받으면 맞았는지 알 길이 없지만,
축을 따로 받으면 "축끼리 앞뒤가 맞는가"를 기계적으로 확인할 수 있다.

프롬프트에 `[표준 문구 보정]` 블록을 넣어 관행적 품질·호환 문구가 blocker로 잘못 잡히는
것을 15건 중 6건 → **0건**으로 줄였다.

### 1-3. 예시를 어떻게 고를 것인가 — 앵커 풀

few-shot 예시(앵커)를 사람이 일일이 검토하는 건 끝이 없다. 대신 **같은 입력을 zero-shot으로
3회 돌려 만장일치한 것만** 통과시켰다. 100건 중 81건 통과.

한때 라벨링 결과를 앵커에 되먹여 192건으로 늘렸다가 **되돌렸다.** 이유가 셋이다.

1. 추가분 92건 중 88건이 한 문서에서 나와 다양성이 무너졌다(문서 점유율 13% → 49%)
2. 실행 순서가 결과를 바꾼다 (경로 의존성)
3. 누적하면 **결국 전체가 앵커가 되어** 학습/평가 분리가 불가능해진다

**배울 점: 자기 출력을 입력으로 되먹이면 평가가 무너진다.** `anchor_pool_v2`(100건)에서
동결하고 실행 중 절대 바꾸지 않는다.

⚠️ 3회 일치는 **안정성이지 정확성이 아니다.** 같은 오답을 세 번 반복해도 통과한다.
실제로 사람이 검토한 건 11건뿐이고, 논문에서는 출처 등급을 나눠 보고한다.

### 1-4. 대규모로 어떻게 돌릴 것인가

- **Batch API** — 동기 실행의 50% 가격. 제출 후 컴퓨터를 꺼도 된다
- **100건 단위 청크** — 단일 배치와 비용 차이가 200원인데, 100건마다 품질을 볼 수 있다
- **프롬프트 캐시** — 고정 앵커일 때만 앵커 블록이 캐시된다(6,912원 → 2,619원)

실측 비용: 앵커 스크리닝 2,300원 + 전수 7,500원 + 재시도 40원, **누적 약 18,900원.**

**겪은 문제 — 생성 반복(degeneration).** 한국어로 시작해 다른 언어로 이탈하거나, 닫는
괄호를 무한 반복해 JSON이 깨졌다. 실패율은 배치 0.43% / 동기 3.3%였고 재시도로 전부 회수했다.

### 1-5. 결과를 어떻게 확정할 것인가

원본 실행 결과를 그대로 쓰지 않고 **한 번 정리**한다.

| 정리한 것 | 내용 |
|---|---|
| 고정 규칙 위반 보정 | 6건(0.6%). `reasoning`을 전건 읽어보니 6건 모두 근거가 규칙 쪽을 지지 |
| 균일 스키마 | 모든 행이 같은 키 + `execution_path`, `source_run` 명시 |
| 요구사항 유형 정규화 | 원본 표기 **60종 → 정본 12종** |

유형 정규화가 특히 인상적이었다. 60종으로 흩어져 있을 때는 "기능 요구사항" 48.5% /
"기능" 35.0% / "기능 요구사항(SFR)" 10.5%로 갈렸는데, **이건 유형 차이가 아니라 출처
문서의 차이**였다. 12종으로 묶자 통상수용 비율이 단조롭게 정렬됐다.

```
시스템장비구성 1.3% < 성능 17.8% < 기능 36.1% < ... < 품질 75.0% < 프로젝트관리 76.2%
```

원가가 붙는 유형이 낮고 표준 문구가 많은 유형이 높다. **정규화가 잡음을 지운 게 아니라
신호를 드러냈다.**

### 1-6. 동결 — 왜 해시를 대조하는가

`label_dataset_v2.jsonl`은 **동결 데이터셋**이다. 읽을 때마다 SHA-256을 대조하고
다르면 **분석이 도는 대신 실패한다.**

```python
from scripts.labeling.label_dataset import load_label_dataset
rows, meta = load_label_dataset()
```

**배울 점: 실험을 비교하려면 모두가 같은 데이터를 봐야 하는데, 조용한 변경은 눈치채기
어렵다.** 바꿔야 하면 파일을 고치는 게 아니라 **새 버전을 만들고** 해시를 갱신한다.
해시 갱신은 "데이터셋을 교체하겠다"는 선언이라 기록을 남긴다.

### 1-7. 결함을 어떻게 다룰 것인가

[`../issues/`](../issues/)에 8건을 정리했다. 처음엔 목록이 실제 위험보다 커 보였는데,
**전제 하나를 밝히자 절반이 성격을 바꿨다.**

> 학습 입력은 **요구사항 원문**이다. 문서 ID·기관·유형·건수는 특징으로 쓰지 않는다.

| 구분 | 이슈 |
|---|---|
| 학습에 직접 영향 | **004**(라벨 품질), **005**(희소 값) |
| 평가 보고에서 다룸 | 003, 006 |
| 분석용으로만 | 001, 002 |
| 입력에 안 넣음 | 007 |

**배울 점: 결함의 심각도는 전제에 딸려 있다.** 무엇을 입력으로 쓸지 정하지 않은 채
결함을 나열하면 실제보다 위험해 보인다.

그리고 두 건은 **관측은 맞았는데 해석이 틀렸던** 사례로 남겼다.

- 문서별 분포 편차(003)를 결함으로 적었으나 → **분포 차이는 사실이다.** 어떤 RFP는 정말 더 쉽다
- 문구 반복(006)을 "누수"로 적었으나 → **중복도 누수도 아니다.** 배포에서도 같은 조항이
  나오므로 알아보고 답하면 그건 정답이다

## 2. 평가는 어떻게 나누는가

### 2-1. 문서 단위 LODO 10겹

행을 무작위로 섞지 않는다. 같은 RFP의 비슷한 요구사항이 학습과 평가 양쪽에 갈라져
들어가면 누수가 된다.

```
fold마다:  학습 8문서 / 검증 1문서 / 평가 1문서
```

- **왜 8:2가 아닌가** — 문서가 10개뿐이라 평가에 2문서만 오른다. fold 기준선이
  34.3%~79.2%로 벌어져 있어 **어느 2개가 걸리느냐로 결과가 뒤집힌다**
- **왜 검증 문서가 따로 필요한가** — 평가 문서를 보고 하이퍼파라미터나 조기 종료 시점을
  고르면 그 문서는 더 이상 "처음 보는 문서"가 아니다 (**선택 누수**)
- **왜 회전인가** — 한 문서를 고정하면 그 난이도가 모든 fold에 같은 방향으로 스며든다.
  한 칸씩 밀면 상쇄되고, 무작위가 아니라 seed 없이 재현된다

```powershell
python -m scripts.evaluation.folds
```

### 2-2. 기준선은 **둘**이다

| 이름 | 정의 | 성격 |
|---|---|---|
| **Dummy** | 학습 집합의 최빈 클래스를 찍는다 | 실제로 **배포 가능한** 모델 |
| **oracle** | 평가 문서 **안에서의** 최빈 비율 | 정답을 본 값. **그 fold가 얼마나 쉬운가**의 눈금 |

이 데이터에서 학습 최빈은 늘 `통상수용`인데 **문서별 최빈은 다르다.** defense·ccrs·genai는
앵커 제외 후 ccrs·genai는 `견적반영`이 최빈이라 2개 fold에서 둘이 갈린다.

**섞어서 하나로 보고하면 "모델이 기준선을 넘었는가"가 흐려진다.**

### 2-3. fold 난이도와 문구 반복은 **독립이 아니다**

```
oracle 기준선 vs 반복 문구 노출률 상관  r = 0.635
```

어려운 문서(defense·ccrs·genai)는 반복 노출이 0~4.5%인데, 쉬운 문서(koen·mfds)는
20~24%다. **쉬운 fold가 표준 문구라는 공짜 점수까지 더 받는다.**

원인을 생각하면 당연하다 — 인프라 증설 사업은 표준 문구가 많고 그래서 통상수용도 많다.
같은 원인이 두 지표에 나타난 것이다.

**주의: 두 교란이 겹치므로 각각 따로 할인하면 이중 할인, 하나만 보면 과대평가가 된다.**

## 3. 어떤 지표를 봐야 하는가

### 3-1. 주 지표 — macro F1

**클래스별 F1을 구한 뒤 단순 평균.** 건수를 전혀 반영하지 않는다.

앵커를 제외한 mfds 평가 문서(181건) 실측이다.

| 클래스 | 건수 | F1 |
|---|---:|---:|
| 통상수용 | 128 | 0.818 |
| 견적반영 | 24 | **0.200** |
| 계약·질의검토 | 29 | 0.500 |

```
macro F1 = (0.818 + 0.200 + 0.500) / 3 = 0.506   <- 클래스마다 1/3씩
정확도   = 128건짜리가 지배            = 0.691
```

**같은 예측인데 0.51과 0.69로 갈린다.** 전체의 13%인 `견적반영`을 놓치면 macro는
그것만으로 약 0.20이 깎이지만, 정확도는 멀쩡해 보인다.

### 3-2. 정확도는 보조 — 왜 위험한가

Dummy(최빈만 찍기)의 실측이다.

```
정확도                 0.506   <- "절반은 맞힌다"
macro F1               0.219
계약·질의검토 recall    0.000   <- 정작 검토할 조항은 하나도 못 찾는다
```

정확도만 보면 그럴듯한데, **세 클래스 중 둘을 아예 예측하지 않는다.** 실무에서 쓸모가 0인
모델이 정확도 0.49를 낸다.

> micro F1은 단일 라벨 다중분류에서 **정확도와 항상 같다.** 따로 볼 이유가 없다.

### 3-3. `계약·질의검토` recall — 따로 본다

이 라벨을 놓치면 검토 없이 넘어가는 조항이 생긴다. **다른 두 라벨의 오류와 비용이 다르다.**
그래서 평균에 섞지 않고 따로 낸다.

### 3-4. fold 점수 읽는 법

**절대 점수를 fold끼리 비교하지 않는다.** 대신 이렇게 본다.

1. **기준선 대비 개선폭** — koen에서 70%와 defense에서 62% 중 뭐가 나은가? 기준선이
   79.2%와 34.3%이므로 후자가 훨씬 낫다
2. **집계는 두 방식 다** — fold 단순 평균(작은 문서도 같은 무게)과 건수 가중(큰 문서 셋이
   전체의 48.6%). 하나만 쓰면 어느 쪽이든 오해를 만든다
3. **세 갈래 점수** — 전체 / 반복 문구 제외 / 반복 문구만. 임계값(0.6)을 **반드시 함께 적는다**
   (0.5면 16.3%, 0.8이면 4.9%로 결론이 크게 바뀐다)

세 갈래의 실측이다.

| 평가 문서 | 전체 | 반복 제외 | 반복만 | 반복 건수 |
|---|---:|---:|---:|---:|
| mfds | 0.506 | 0.460 | **1.000** | 43 |
| ccrs | 0.676 | 0.676 | — | **0** |
| incheon | 0.525 | 0.533 | 0.000 | **1** |

mfds는 반복 문구에서 만점, 나머지에서 0.460이다. **전체 0.506만 보고 "처음 보는 RFP에
일반화된다"고 하면 주장이 실제보다 강해 보인다.**

⚠️ **건수를 반드시 같이 본다.** incheon의 0.000은 1건짜리라 성능이 아니라 표본 크기의
산물이다. ccrs는 0건이라 점수 자체가 없다.

### 3-5. 효과인가 잡음인가

문서가 10개뿐이라 fold 분산이 크다. **평균 차이가 fold별 편차 폭에 비해 작으면 효과가 아니다.**

| 비교 | 평균 | 편차 폭 | 우세 | 판정 |
|---|---:|---:|---:|---|
| `class_weight` 없음 → balanced | **+0.080** | 0.254 | 9/10 | 효과 |
| 표현 word → char | +0.020 | 0.205 | 7/10 | 보류 |
| 학습 문서 8 → 9 | +0.001 | 0.105 | 6/10 | 잡음 |

**크기 차이가 약 80배다.** 어느 파라미터를 먼저 만질지는 이런 비교로 정한다. 그리드서치로
최고 조합만 뽑으면 이 순서가 보이지 않는다.

## 4. 되풀이되는 원칙 넷

### ① 추론보다 측정

- `산출정보` 열을 넣으려면 9,000원이 필요했는데, **세어보니 채워진 게 35.5%뿐**이라 기각
- "쏠린 fold에서는 balanced가 손해일 것" → 방향은 맞았지만 **크기가 틀려서 결론이 반대**였다

그럴듯한 추론이 6초짜리 실험보다 못했던 사례가 반복해서 나온다.

### ② 한 번에 하나만 바꾼다

이 프로젝트의 질문은 "최고 점수가 몇 점인가"가 아니라 **"복잡하게 만든 값을 했는가"**다.
그리드서치는 점수를 주지만 **어느 선택이 효과를 냈는지 설명하지 못한다.**

### ③ 동결하고 해시로 지킨다

앵커 풀도, 라벨 데이터셋도 동결한다. 조용히 바뀌면 눈치채기 어렵고, 그러면 실험을
비교할 수 없다.

### ④ 관측과 해석을 분리한다

숫자를 먼저 보고 이름을 나중에 붙이다 보면 "누수" 같은 강한 단어가 먼저 나온다.
**관측이 맞아도 해석은 틀릴 수 있다.** 틀린 해석은 지우지 말고 정정 기록으로 남긴다.

## 부록 — 자주 헷갈리는 것

### 불균형 vs 분포 이동

|  | 불균형 | 분포 이동 |
|---|---|---|
| 무엇 | 클래스 건수가 다르다 | **학습과 평가의 분포가 다르다** |
| 이 데이터 | 50/24/26, 2.12배 → 심하지 않음 | fold마다 최대 **34%p** 어긋남 |
| 처방 | `class_weight` | **`class_weight`로 못 고친다** |

mfds에서 `견적반영` F1이 0.196이었던 게 후자의 예다. 모델은 25%를 기대하고 나갔는데
실제로는 13%였고, **개수는 거의 맞췄지만(예측 26 / 정답 25) 어느 것인지를 못 맞혔다.**
소수라서 무시당한 게 아니라 **구분이 안 되는 것**이다.

### 누수 vs 표준 문구 반복

- **누수** = 있어선 안 될 정보가 새는 것
- **표준 문구 반복** = 서로 다른 사업의 별개 요구사항이 문구를 공유하는 것.
  **배포에서도 똑같이 일어난다.** 알아보고 답하면 정답이다

남는 문제는 **점수 하나에 두 능력이 섞인다**는 것뿐이고, 대응은 데이터가 아니라 보고 쪽이다.

### macro / weighted / micro

| | 계산 | 이 프로젝트에서 |
|---|---|---|
| **macro** | 클래스별 F1의 **단순 평균** | **주 지표** |
| weighted | 건수로 가중 | 정확도와 비슷하게 움직여 잘 안 씀 |
| micro | = **정확도** | 볼 이유 없음 |

### Dummy vs oracle

- **Dummy** — 학습 최빈을 찍음. **배포 가능**. 넘지 못하면 아무것도 못 배운 것
- **oracle** — 평가 문서 안 최빈. **반칙**. fold 난이도의 눈금일 뿐
