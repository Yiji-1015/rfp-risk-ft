## 9. Pure TF-IDF 앵커 검색기 및 In-Memory 검색

### 결정

Dynamic Few-shot 앵커링 시 별도의 무거운 외부 벡터 DB(Chroma, Qdrant 등)나 딥러닝 임베딩 모델 서버 없이, Pure TF-IDF 및 `scikit-learn` 기반 코사인 유사도 연산으로 앵커를 동적 인출한다.

- 희소 벡터(Sparse Vector) 표현: 어절(Word) 1~2gram 및 자소/문자 n-gram 결합
- `sublinear_tf=True`를 적용하여 고빈도 단어의 편향을 완화
- In-Memory 상에서 $O(N)$ 코사인 유사도 즉시 연산 (1,024건 대상 < 0.001초)

### 근거

소규모 RFP 요구사항 데이터셋 특성상 특정 계약/기술 독소 키워드(`무상`, `지체상금`, `250TB`, `K-RMF`, `상주`)의 정확한 일치(Lexical Match)를 잡는 것이 실무 위험 판정에 가장 직관적이고 효과적이다. 외부 인프라 부하 없이 독립 실행이 가능하다.

## 10. Dynamic Few-shot 앵커링 시 데이터 누수 하드 차단

### 결정

Dynamic Few-shot 프롬프트를 구성할 때 Target 요구사항의 출처 문서와 동일한 `document_id`를 가진 앵커는 유사도 계산 대상에서 하드 필터링(`similarities[idx] = -1.0`)하여 제외한다.

```python
# target과 동일한 document_id를 가진 앵커는 자동 차단
if anchor.get("document_id") == target_doc_id:
    similarities[idx] = -1.0
```

### 근거

동일 RFP 문서 내부의 다른 요구사항을 앵커 예시로 주입할 경우, 기관 고유의 서식이나 문맥이 그대로 유입되어 평가(Validation/Test) 시 문서 단위 일반화 성능을 왜곡할 수 있다.

## 11. 3개 대표 RFP 기반 1차 라벨링 비교 파일럿

### 결정

전체 1,024건 라벨링에 앞서 대표 성격의 RFP 3개 문서(총 259건)를 선별하여 Zero-shot vs Pure TF-IDF Dynamic Few-shot 비교 파일럿을 먼저 수행한다.

- 대상 문서: `kac_ai_work_platform` (86건), `incheon_airport_digital_work` (78건), `ccrs_ai_platform` (95건)

### 근거

공공 SI 수주 현실상 불합리해 보이는 문구라도 10개 기관 공통 관행인 조항(통상수용)과 특정 사업의 기습 독소조항(계약검토)을 구분하기 위해, 앵커링 도입 전후의 라벨 변화 양상을 눈으로 직접 확인하고 라벨링 기준을 유동적으로 조정하기 위함이다.

## 12. In-Context Few-Shot 프롬프트 고도화 계획 (llm-wiki 연계)

### 결정

Dynamic Few-shot 앵커 주입 시 단순 예시 나열 방식에서 벗어나, Target 요구사항과 앵커 간의 **공통 핵심 키워드(Overlap Terms)** 및 **TF-IDF 유사도 점수**를 프롬프트 구조에 함께 포함시키는 고도화 방안을 후속 파이프라인에 반영한다.

### 근거

인-컨텍스트 학습(In-Context Learning) 시 LLM이 단순히 앵커의 정답만 모방하는 대신, "어떤 키워드 유사성 때문에 이 예시가 인출되었는지" 맥락을 인지하게 만들어 주 라벨 판정의 인과성과 일관성을 극대화하기 위함이다.

## 13. 3개 대표 RFP 라벨링 파일럿(259건) 결과 및 단일 모델 통제 원칙

### 결정

3개 대표 RFP(259건)에 대해 Zero-shot vs Pure TF-IDF Dynamic Few-shot 라벨링 비교 실험을 완수하였으며, 연구의 엄밀성과 통제 변수(Controlled Experiment) 유지를 위해 100% 동일한 단일 LLM(`gemini-3.5-flash-lite`)을 사용하였다.

- **실험 수치 결과**:
  - 대상 문서: `kac_ai_work_platform` (86건), `incheon_airport_digital_work` (78건), `ccrs_ai_platform` (95건)
  - 총 요구사항 수: 259건
  - 라벨 일치 건수: 182 / 259건
  - 전체 라벨 일치율 (Agreement Rate): **70.27%**
  - 판정 변동 건수 (Action Shift): **77건 (29.73%)**

### 연구 인사이트 및 관행 반영 효과

1. **Zero-shot의 과도한 보수적 방어 판정**: Zero-shot 단독 실행 시 기술 난이도가 높거나 모호한 AI/RAG 요구사항(예: RAG 파이프라인 구축, AI 가드레일, 준실시간 평가 모니터링 등)에 대해 54건을 `계약·질의검토`로 과도하게 매핑함.
2. **앵커링(Few-shot) 도입을 통한 현실적 교정**: 타 공공 RFP 앵커 예시 3개가 프롬프트로 주입되자, LLM이 타 공공기관 구축 사업의 일반적인 SI/개발 공수 범위를 학습하여 `계약·질의검토` 54건 중 **26건(48.1%)이 현실적인 `견적반영`으로 교정**됨.
3. **도메인 통상 관행 반영 확인**: "개별 요구사항만 볼 때는 불합리해 보여도 타 기관 공통 관행인 조항"을 앵커 검색이 성공적으로 포착하여, 실무 현장에 적합한 라벨(통상수용/견적반영)을 부여함을 통계 및 질적 사례로 입증함.

### 발견된 한계 및 향후 개선 대책 (Anchor Label Bias)

- **견적반영 라벨 쏠림 현상 관찰**:
  - Dynamic Few-shot 적용 후 `견적반영` 라벨 비율이 **68.7% (178/259건)**로 증가함.
  - **원인 분석**: RFP 요구사항 문항 특성상 공수/비용 관련 항목이 다수이며, Top-k 유사도 검색 시 `견적반영` 앵커 예시가 과다 주입되어 LLM이 리스크 항목을 과도하게 안일하게 순화(Softening Bias)시킬 위험이 관찰됨.
- **향후 개선 대책 (Balanced Stratified Few-shot)**:
  - 앵커 인출 시 단순 유사도 Top-k만 추출하지 않고, **`통상수용`, `견적반영`, `계약·질의검토` 각 3가지 라벨의 대표 앵커를 1개씩 균형 있게 주입(Stratified Selection)**하여 앵커 라벨 편향을 억제하는 고도화 방안을 2차 전체 라벨링 단계에 적용하기로 결정함.

## 14. 학술 선행연구 기반 층화 퓨샷 검색 (Stratified Few-shot Retrieval) 채택

### 결정

Dynamic Few-shot 앵커 주입 시 발생한 68.7% '견적반영' 라벨 쏠림(Majority Label Bias)을 해결하기 위해, 최신 NLP 학술 문헌(Zhao et al., ICML 2021; Fei et al., ACL 2023; Gao et al., ICLR 2025)에서 입증된 **층화 퓨샷 검색(Stratified Retrieval: 라벨별 1:1:1 비율 강제 인출)**을 2차 비교 파일럿 및 전수 라벨링 알고리즘으로 최종 채택한다.

### 학술적 근거

1. **Zhao et al. (ICML 2021, *Calibrate Before Use*)**:
   - In-Context Learning에서 LLM은 프롬프트 내에 가장 자주 나타난 레이블을 맹목적으로 선호하는 **다수 레이블 편향(Majority Label Bias)**을 가짐을 통계적으로 입증.
2. **Fei et al. (ACL 2023, *Mitigating Label Biases for In-context Learning*)**:
   - 전문 도메인 어휘(예: '단가', '산출물', '일정')가 특정 클래스와 결합될 때 발생하는 **도메인-컨텍스트 레이블 편향(Domain-Label Bias)**을 규명.
3. **Gao et al. (ICLR 2025, *Exploring Imbalanced Annotations for Effective ICL*)**:
   - 앵커 예시의 레이블 불균형이 심할수록 LLM의 **작업 학습(Task Learning)** 능력이 파탄나며, 희소 클래스에 대한 위음성(False Negative)이 급증함을 증명.

### 실행 구현 알고리즘

- 코사인 유사도 상위 Top-3를 맹목적으로 추출하는 방식을 폐기하고,
- 앵커 후보 풀을 `통상수용`, `견적반영`, `계약·질의검토` 3개 라벨 인덱스로 분리하여 **각 라벨별로 쿼리와 가장 유사한 앵커를 1개씩(총 3개, 1:1:1 비율) 추출**하여 프롬프트에 제공함으로써 앵커 레이블 편향을 물리적으로 하드 차단함.

## 15. 예측 가능한 API 예산 제어 및 사전 비용 추정 원칙 (Predictable Budget Control)

### 결정

연구 및 데이터 구축 시 무분별하거나 예측 불가능한 API 비용 지출을 원천 차단하기 위해, **사전 비용 추정(Pre-Execution Cost Estimation)** 및 **예산 상한 캡(Budget Safety Cap)** 원칙을 시스템 운영 표준으로 확정한다.

- **사전 비용 계산 및 명시 (Pre-execution Estimation)**:
  - 대량 LLM API 호출 스크립트 실행 전, `(총 요구사항 수 × 프롬프트당 평균 토큰 수 × 모델 단가)`를 계산하여 **총 예상 비용(원화/달러)을 사전 계산하고 명시**한다.
- **예산 상한 캡 및 안전 멈춤 (Budget Safety Cap)**:
  - 사용자가 사전에 허용한 예상 비용 범위를 넘어서는 대규모 파이프라인의 경우, 자동으로 가동을 멈추고 사용자 승인을 받도록 안전 캡(Cap)을 설정한다.
- **투명한 토큰/비용 로깅 (Transparent Cost Logging)**:
  - API 호출 시 실제 소비된 토큰 수와 소요 비용을 실시간으로 추적 및 기록하여 예측 가능하고 신뢰할 수 있는 비용 제어를 보장한다.

## 16. LLM 출력 스키마 최소화 원칙 (Output Schema Minimization)

### 결정

LLM API 호출 시 출력 스키마를 **연구 목적에 실질적으로 필요한 최소 필드**로만 구성한다. 불필요한 장문 서술 필드를 포함시키면 출력 토큰 수가 폭발적으로 증가하여 비용 대비 효용이 현저히 낮아진다.

**확정 최소 출력 스키마 (3개 필드)**:

| 필드 | 역할 | 형식 |
|---|---|---|
| `primary_action` | 핵심 분류 라벨 (연구의 Y) | Enum: `통상수용` / `견적반영` / `계약·질의검토` |
| `confidence` | 라벨 불확실성 지표 | Enum: `높음` / `보통` / `낮음` |
| `reasoning` | 판단 근거 (앵커 재사용) | **1~2문장 요약형**으로 길이 제한 |

### 제거 필드 및 사유

다음 필드는 연구 핵심 목표(라벨 분류)와 직접적 관련이 낮으며, 출력 토큰을 과도하게 소비하므로 제거한다.

| 제거 필드 | 제거 사유 |
|---|---|
| `evidence` | `reasoning`과 90% 이상 내용 중복 |
| `missing_information` | 라벨링 본질과 무관, 논문 한계절 논의로 대체 가능 |
| `domain_dependency` | 라벨 분류 결정에 직접 영향 없음 |
| `risk_factors.cost_driver` | 현 파일럿 단계에서 과잉 분석 |
| `risk_factors.scope_uncertainty` | 현 파일럿 단계에서 과잉 분석 |
| `risk_factors.responsibility_risk` | 현 파일럿 단계에서 과잉 분석 |
| `risk_factors.acceptance_risk` | 현 파일럿 단계에서 과잉 분석 |

### 기대 효과

- 출력 토큰 수: 건당 약 800~1,000 토큰 → **약 80~100 토큰 (약 10배 감소)**
- 이에 따른 출력 비용도 약 10배 절감
- `reasoning`을 1~2문장으로 제한하므로, 앵커 주입 시 프롬프트 길이도 함께 단축됨

### 논문 반영 위치

- 연구 방법: 라벨링 파이프라인 설계 및 출력 구조
- 한계 및 후속 연구: 세부 리스크 요인 분류는 추후 2단계 검토 워크플로우에서 수행

## 17. 결정 16의 코드 반영과 스키마 v2.0.0 동결

### 결정

결정 16은 문서에만 반영돼 있었고 `scripts/labeling/label_schema.py`는 여전히 8필드 스키마였다. 유료 전수 라벨링 전에 코드를 결정 16에 맞추고 `SCHEMA_VERSION`을 `2.0.0`, `PROMPT_VERSION`을 `claude-rfp-risk-v2`로 올린다.

- `LabelResult`는 `requirement_uid`, `primary_action`, `reasoning` 3개 필드만 유지한다. `requirement_uid`는 분석 필드가 아니라 입력-응답 정합성 검사용 에코 필드이므로 결정 16의 제거 대상이 아니다.
- `MissingInformation`, `DomainDependency`, `RiskFactors` 모델과 `evidence` 필드를 삭제한다. `extra="forbid"`가 유지되므로 구 스키마 출력은 검증 단계에서 거부된다.
- 결정 16이 남기기로 했던 `confidence`도 함께 제거한다(아래 별도 항 참조).
- `reasoning`에 `max_length=300`(`REASONING_MAX_LENGTH`)을 둔다. 한국어 1~2문장은 통상 60~120자이므로 정상 출력은 걸리지 않고, 장문 이탈만 차단한다.
- 시스템 프롬프트에서 삭제된 필드 지시(규칙 2~5)를 제거하고, `reasoning` 길이 제한을 명시한다. 근거 인용은 별도 배열 대신 `reasoning` 안에서 짧게 처리한다.

### `confidence` 제거 (결정 16 수정)

결정 16은 `confidence`를 최소 스키마에 남겼으나, 코드 반영 시점에 제거하기로 변경한다. 비용 때문이 아니라 측정 타당성 때문이다.

1. **실행 조건에 종속된 값이다.** 같은 요구사항이라도 zero-shot과 dynamic few-shot에서 다른 확신도가 나온다. 결정 9~14의 통제 비교는 라벨과 분할을 고정한 채 전략만 바꾸는 설계인데, `confidence`로 사람 감사 표본을 선정하면 조건마다 감사 표본이 달라져 두 조건이 서로 다른 테스트셋을 갖게 된다.
2. **더 나은 불확실성 지표가 이미 관측된다.** 조건 간 판정 변동(결정 13에서 관측된 77건 Action Shift)과 반복 실행 라벨 일치율은 자기 보고가 아닌 관측값이다. 앵커 후보 선정과 도전 표본 구성은 여기서 도출하는 것이 타당하다.
3. **앵커링 도입 전제와 중복이다.** 판정이 흔들린다는 사실을 전제로 앵커링을 도입하는 실험에서, 모델의 자기 보고 확신도는 독립적인 정보를 더하지 않는다.

부수적으로 결정 16 표기(`보통`)와 기존 코드 표기(`중간`)의 불일치 문제도 함께 소멸한다.

**감수하는 손실**: 단일 조건 1회 실행만으로 검토 우선순위를 정해야 하는 상황(신규 RFP 1건 데모)에서는 건별 불확실성 신호가 없다. 연구 단계에서는 항상 2개 이상 조건을 실행하므로 문제되지 않으며, 데모 단계에서 필요해지면 2단계 워크플로에서 확장 스키마로 받는다.

### 근거

스키마 불일치 상태로 `--execute`를 실행하면 결정 16이 없앤 필드를 그대로 생성해 예상 대비 약 10배의 출력 비용이 발생한다. 결정 15의 사전 비용 추정도 실제 출력 구조와 어긋나 무의미해진다. 파일럿 결과를 나중에 폐기하지 않으려면 첫 유료 호출 전에 스키마를 동결해야 한다.

### 영향 범위

`SCHEMA_VERSION` 1.0.0으로 생성된 기존 산출물(`reports/archive/`)은 재검증 대상이 아니라 보존 대상이다. v2.0.0 결과와 직접 비교하지 않고, 비교가 필요하면 `primary_action` 기준으로만 대조한다.

## 18. 앵커 검색기의 라벨링 파이프라인 연결

### 결정

`scripts/labeling/anchor_retriever.py`가 라벨링 실행 경로에 연결되어 있지 않아 Claude 기준으로는 zero-shot만 실행 가능했다. `run_claude_labeling.py`에 `--strategy`를 추가해 §8.2의 비교를 실행 가능한 상태로 만든다.

| 전략 | 인출 방식 | 근거 |
|---|---|---|
| `zero-shot` (기본) | 앵커 없음 | 비교 기준선 |
| `fewshot-similarity` | 유사도 Top-k | 결정 13 |
| `fewshot-stratified` | 라벨별 1개씩 | 결정 14 |

결정 14가 층화 인출을 최종 채택했지만 `fewshot-similarity`도 남긴다. 결정 13에서 관측된 견적반영 68.7% 쏠림이 층화 인출로 실제 완화되는지 보이려면 두 방식의 결과가 모두 있어야 하며, 이 대비가 논문의 근거가 된다.

### 앵커 배치 위치

앵커 블록은 캐시되는 system 블록이 아니라 user 메시지에 넣는다.

1. 앵커는 입력마다 달라진다. system에 넣으면 캐시 프리픽스가 매 건 깨져 결정 15의 비용 통제가 무너진다.
2. system 프롬프트가 전략별로 달라지면 zero-shot과 few-shot의 차이가 앵커 유무 하나로 좁혀지지 않는다. §9.3의 통제 비교 조건을 지키기 위해 system은 전략과 무관하게 동일하게 유지한다.

앵커 사용 지침("사례의 판정을 그대로 따라가지 말 것", "제공 주체·상한·책임이 다르면 판정도 달라야 함")도 같은 이유로 앵커 블록 안에 둔다. §11.11과 §11.12의 유사 문구 오판정·앵커 오류 대응에 해당한다.

### 앵커 풀 감사 게이트

`scripts/labeling/anchor_pool.py`가 로딩 시점에 다음을 강제한다.

- `review_status`가 `검토완료`인 행만 프롬프트에 들어간다(§11.13 앵커 풀 오염 방지).
- 한 파일에 여러 `pool_version`이 섞이면 실패한다.
- `fewshot-stratified`는 세 라벨 모두에 앵커가 있어야 실행된다. 하나라도 비면 층화가 성립하지 않고 결정 14가 막으려던 다수 라벨 편향으로 되돌아가므로 사전에 멈춘다.
- 풀 파일의 SHA-256을 run manifest에 기록한다(§11.15).

### 재현성 기록

- run manifest에 `strategy`, 검색기 설정, 앵커 풀 메타데이터를 남기고, 이 값들이 다르면 기존 `output-dir`에 이어쓰기를 거부한다. 한 `results.jsonl`에 서로 다른 전략의 결과가 섞이면 조건 간 판정 변동 분석이 무너진다.
- 각 결과 행에 실제 주입된 앵커의 UID·라벨·유사도·공통 어휘를 남긴다. §11.12의 앵커 perturbation 분석에 필요하다.
- dry-run에서도 앵커 풀을 검증하고 주입될 앵커의 라벨 분포를 출력한다. 앵커 편향은 유료 실행 전에 확인해야 한다.

### 부수 수정: 문자 n-gram 누락

검색기의 벡터라이저가 `analyzer='word'` 하나였다. 결정 9("어절 및 자소/문자 n-gram 결합")와 PROJECT_DIRECTION §9.2("문자 n-gram을 반드시 포함한다")를 코드가 따르지 않은 상태였으므로, 어절 1~2gram과 문자 3~4gram(`char_wb`)을 결합한 표현으로 수정한다. 두 블록이 각각 L2 정규화되므로 결합 벡터의 코사인 유사도는 두 유사도의 평균과 같다(가중치 50:50). 한국어 RFP의 띄어쓰기 변형, 조사 변화, 영문·숫자 코드(`K-RMF`, `250TB`)를 잡는 것이 문자 n-gram의 역할이며, 이 표현으로 생성된 결과는 아직 없으므로 재현성 영향은 없다.

## 19. 사고(thinking) 설정의 명시와 실행 조건 기록

### 결정

Claude 호출 시 `thinking`을 항상 명시해서 전송하고, `--thinking {adaptive,disabled}`로 노출하며 run manifest와 건별 metadata에 기록한다. 기본값은 `adaptive`다.

- `ClaudeSettings.thinking`을 추가하고, Sonnet 5 요청에 `thinking: {"type": ...}`을 항상 포함한다.
- Haiku 4.5는 adaptive thinking과 effort를 모두 거부하므로 두 파라미터를 함께 생략하고, 기록에는 `null`로 남긴다.
- `effort` 선택지에 Sonnet 5가 지원하는 `xhigh`, `max`를 추가한다.
- `max_tokens` 기본값을 4096에서 16000으로 올린다.

### 근거

Sonnet 4.6까지는 `thinking`을 생략하면 사고가 꺼졌지만, **Sonnet 5부터는 생략이 곧 adaptive thinking 활성화**다. 코드가 이 파라미터를 한 번도 넘기지 않았으므로 현재 파이프라인은 아무도 결정하지 않은 상태로 사고를 수행하고 있었다. 세 가지 문제가 있다.

1. **결정 16의 비용 모델이 성립하지 않는다.** 결정 16은 출력을 건당 80~100 토큰으로 보고 10배 절감을 예상했으나, 실제 청구되는 출력은 `사고 토큰 + 라벨 토큰`이다. 사고량에 따라 절감분의 상당 부분이 상쇄된다.
2. **`max_tokens`가 사고와 응답을 합쳐서 제한한다.** 기존 4096에서 사고가 상한에 근접하면 응답이 잘려 `stop_reason="max_tokens"`가 되고, 해당 건은 비용만 지불한 채 error로 기록된다. 상한은 과금 대상이 아니므로 16000으로 올려 이 실패 모드를 제거한다.
3. **실행 조건 기록이 비어 있었다.** §11.15는 프롬프트·모델·실행 조건의 보존을 요구하는데, manifest에 사고 설정이 없으면 같은 manifest로 서로 다른 조건의 실행이 재현된다.

기본값을 `adaptive`로 둔 이유는 현재 동작과 같아서가 아니라, 파일럿에서 사고의 비용과 품질 효과를 실측해야 하기 때문이다. 기본을 `disabled`로 두면 측정 대상 자체가 사라진다. 실측 후 전수 라벨링의 값은 별도로 확정한다.

### 관측 지점

건별 진행 출력에 `out`(출력 토큰), `cache_write`, `cache_read`를 노출한다. 라벨 자체는 100 토큰 안팎이므로 `out`이 그보다 크게 나오면 차이가 사고 비용이다. Anthropic API는 사고 토큰을 별도 필드로 보고하지 않으므로 이 차이가 유일한 관측 수단이다.

### 미해결: 프롬프트 캐시 최소 길이

Sonnet 5의 캐시 최소 프리픽스는 1,024 토큰이고 미달 시 오류 없이 캐시가 생성되지 않는다. 현재 캐시 대상은 550자 한국어 system 프롬프트 하나뿐이라 임계값 근처이며, 실제로 캐시가 걸리는지는 확인되지 않았다. 앵커는 user 메시지에 있어(결정 18) 캐시 프리픽스를 늘려주지 않는다. 파일럿 실행의 `cache_write`가 0이면 미달이 확정되며, 이 경우 `cache_control` 선언은 비용에 아무 영향을 주지 않는다.

## 20. 가격 기준 주 라벨과 보조 축 분리 (스키마 v3.0.0)

### 배경: 파일럿 40건에서 관측된 라벨 혼입

Claude zero-shot 파일럿(40건, 스키마 v2)의 `계약·질의검토` 32건을 표면 근거로 분해한 결과다.

| 표면 근거 | 건수 | 비율 |
|---|---:|---:|
| 책임가중(책임·귀책·지체상금·하자) | 9 | 28% |
| 범위열림(무상·추후협의·필요시) | 8 | 25% |
| 검수불명(검수·정확도·성능기준) | 7 | 22% |
| **근거 0개** | **15** | **47%** |

근거가 하나도 걸리지 않은 15건은 전부 기술 구축·컨설팅 범위였다(`AI 통합 포털 기능 구현`, `모델 테일러링`, `폐쇄망 LLM 선정 및 도입`, `MCP 기반 AI 연계 표준 정의`, `비전 및 전략수립` 등). 계약 문구가 없는데 `계약·질의검토`로 판정된 것이다.

즉 `계약·질의검토` 하나가 두 가지를 담고 있었다.

| 성격 | 건수 | 실무 조치 |
|---|---:|---|
| 계약 조항이 열려 있음 | 17 | 법무 검토, 계약 질의, 예비비 |
| 기술 범위가 닫히지 않음 | 15 | 요건 구체화 요청, 가정·제외사항 명시 |

이는 §7.2가 경고한 혼동("도메인 난이도는 계약 독소성과 같은 개념이 아니다")이 실제로 발생한 것이며, §11.6("단일 라벨은 이유를 잃는다")의 사례다. 판정이 틀린 것이 아니라 라벨이 이유를 잃었다.

### 결정 1: 주 라벨을 가격 산정 가능성으로 재정의한다

라벨 수는 3개로 유지하되, 정의를 §5.1의 핵심 질문에 정렬한다. 기존 프롬프트는 §5.1을 묻지 않고 라벨 이름의 뜻만 설명했다.

| 라벨 | 가격 기준 정의 |
|---|---|
| `통상수용` | 별도 추가 원가가 붙지 않는다. 기본 공수에 포함된다 |
| `견적반영` | 추가 원가가 붙지만 원문 정보만으로 계산할 수 있다 |
| `계약·질의검토` | 원가를 계산할 수 없다. 범위·책임·기준이 닫혀 있지 않다 |

이 프레임에서 위 두 무더기는 주 라벨 관점에서 동일하다(둘 다 계산 불가). 따라서 라벨을 쪼개지 않고, *왜* 계산 불가인지를 보조 축으로 뺀다.

금액 자체는 LLM에게 묻지 않는다. 한국 공공 SI 단가를 모르므로 지어낼 뿐이다. 계산 가능성만 판단시킨다. 금액 밴드는 사람 감사에서만 사용하며, 3지선다보다 실무자가 일관되게 답하기 쉬운 형태다.

### 결정 2: 보조 축 3개를 추가한다 (스키마 v3.0.0)

전부 짧은 enum이므로 결정 16의 출력 최소화 취지에 반하지 않는다. 결정 16이 막으려던 것은 장문 서술 필드였다. 파일럿 실측에서 출력이 건당 166토큰(사고 66 포함)에 불과했으므로 증가분은 30~40토큰 수준이다.

| 필드 | 값 | 역할 |
|---|---|---|
| `cost_basis` | 없음/인력/장비·인프라/라이선스/외주·전문기관/복합 | 추가 원가의 계산 근거 |
| `blocker` | 없음/계약조항/기술범위/도메인정답 | 계산 불가의 원인. 실무 조치를 가름 |
| `domain_dependency` | 높음/보통/낮음 | §7.2의 보조 축 |
| `build_difficulty` | 높음/보통/낮음 | 도메인을 걷어낸 순수 구축 난이도 |

`build_difficulty`는 반사실 질문으로 정의한다 — "발주기관이 업무 지식·데이터·정답 기준을 모두 제공한다고 가정할 때의 구축 난이도". 이 가정 없이 물으면 도메인 난이도와 섞인다. `AI 통합 포털 기능 구현`은 도메인 지식을 다 줘도 공수가 크고(구축 높음/도메인 낮음), `Agent 채권양수도 추론`은 채권 실무 없이는 정답 정의부터 막힌다(도메인 높음). 두 축이 분리되어야 이 차이가 드러난다.

### 결정 3: `domain_dependency` 복원 (결정 17 일부 수정)

결정 17에서 "라벨 분류에 직접 영향 없음"을 이유로 제거했으나, 문서 간 재출현률 분석이 이 판단을 뒤집었다.

| 유형 | 문서 간 재출현률 | 해석 |
|---|---:|---|
| 품질·프로젝트관리·테스트 | 67~83% | 도메인 의존 낮음 — 기관 무관 SI 문구 |
| 제약사항·데이터 | 31~35% | 중간 |
| 기능·인터페이스·인프라·AI | **0.0%** | 도메인 의존 높음 — 기관 업무 자체 |

기능 요구사항 202건 중 문서 간 재출현이 **0건**이다. 낮은 것이 아니라 없다. 겹치지 않는 이유는 그 기관 업무를 서술하기 때문이며, 도메인 의존과 재출현률은 같은 현상의 두 얼굴이다. 도메인 의존은 장식이 아니라 데이터 구조를 설명하는 축이었다.

다만 복원 방향은 LLM 출력 필드 복원에 그치지 않는다. **재출현률은 LLM 없이 0.5초에 계산되므로 도메인 의존의 독립 검증 지표로 쓴다.** LLM의 `domain_dependency` 판정과 계산된 재출현률을 대조하면, 보조 축의 타당성을 유료 호출 없이 확인할 수 있다.

### 결정 4: 기준 수행사 역량을 페르소나에 명시한다

§4.1은 페르소나가 아는 것과 모르는 것을 규정했으나 **실행 역량**을 규정하지 않았다. 같은 요구사항도 사내 AI 팀이 있는 대형 SI와 소규모 업체가 다르게 값을 매기므로(§11.10), 역량이 비어 있으면 각 판정이 암묵적으로 다른 회사를 상정한다.

기준을 "통상적인 중견 수행사"로 고정하고 프롬프트·감사 지침에 동일 문구를 사용한다.

- 자체 수행 가능: 웹·시스템 개발, DB, API 연계, 인프라 구축, 상용 LLM API와 공개 모델을 활용한 RAG·검색 구축, 경량 모델 파인튜닝
- 자체 수행 어려움: 모델 사전학습, 도메인 정답 데이터 자체 구축, 특수 인증 취득
- 사내 AI 전담 연구조직 없음. AI 인력은 프로젝트 단위 편성
- 발주기관 업무 도메인 지식 없음

### 실험 설계상의 위치

이는 §8.2가 비교 대상으로 예고한 "위험 요인 분해 후 주 라벨 산출"에 해당한다. §7.1의 분해 항목이 추상적이어서 무엇을 물을지 비어 있었는데, 가격 프레임이 그 빈칸을 채웠다.

기존 v2 파일럿 40건(310원 지출)은 폐기하지 않고 **"직접 3분류" 대조군**으로 사용한다. 동일 40건에 v3를 실행하면 §8.2의 비교가 추가 표본 없이 성립한다.

### 영향 범위

- `SCHEMA_VERSION` 2.0.0 → **3.0.0**, `PROMPT_VERSION` v2 → **v3**
- v2로 생성된 결과는 `extra="forbid"`에 의해 v3 검증에서 거부된다. 두 버전의 결과를 한 `results.jsonl`에 섞지 않는다
- 앵커 풀은 v3 확정 후에 구축한다. v2 라벨로 풀을 만들면 위 혼입이 풀에 그대로 굳는다
- §14의 열린 질문 중 "세 주 라벨이 충분히 구분되는가", "`domain_support`·`domain_responsibility`를 정식 필드로 둘 것인가"가 이 결정으로 부분 해소된다

### 두 오판의 원인이 서로 반대다

**`kac:AIP-001` — v3가 과소평가.** 사람 근거: "GDPval-AA ELO 상위 언어모델 4종 이상, 폐쇄망 완전 독립 운용, 영구 또는 최소 5년 라이선스를 동시에 충족할 후보 모델의 존재와 배포권을 입찰 전에 확인해야 한다. 가격 계산보다 기술·라이선스 성립 여부 확인이 선행되어야 한다."

v3의 `blocker` enum(없음/계약조항/기술범위/도메인정답)에 **이 범주를 담을 칸이 없었다.** 모델이 `없음`을 출력한 것은 스키마의 표현력 부족이지 판단 실패가 아니다.

**`koen:CON-003` — v3가 과대평가.** AI 거버넌스·운영체계 설계를 `견적반영`으로 판정했으나 기준 수행사의 통상 컨설팅 범위다. 기술명이 등장한다는 이유로 난이도를 올린 것이며, v3 프롬프트에 **난이도와 주 라벨의 연결 규칙이 없었던** 결과다.

### 결정 1: blocker를 "입찰 전 확인 필요 조건"으로 재정의한다

결정 20은 blocker를 "원가를 계산할 수 없게 만드는 원인"으로 정의했다. 실무자 정의로 교체한다.

> `blocker`는 비용이 발생한다는 뜻이 아니라, **제안·입찰 전에 반드시 확인해야 안전하게 수용할 수 있는 조건**을 뜻한다.

`AIP-001`이 이 차이를 드러낸다. 가격 산정의 문제가 아니라 요구 조건의 **성립 여부** 확인 문제다.

### 결정 2: blocker 범주를 5개로 확장한다

| # | 범주 | 내용 |
|---|---|---|
| 1 | 범위·책임 | 열린 범위, 포괄 책임, 발주기관 재량 추가 수행, 무제한 의무 |
| 2 | 검수·성능 기준 | 합격 기준 부재, 주관적 검수, 합격할 때까지 반복 보완, 결과 보증 |
| 3 | 기술 실현성 | 현재 기술·주어진 환경에서 충족 가능 여부를 먼저 검증해야 하는 조건 |
| 4 | 라이선스·공급 가능성 | 요구 제품·모델·장비·라이선스의 실제 조달 또는 사용 가능성이 불명확 |
| 5 | 특정 제품·공급자 종속 가능성 | 과도하게 구체적인 규격·실적·호환 조건으로 충족 가능한 공급자가 제한될 수 있음 |

4·5는 공공 조달의 실제 현상이며 문헌이나 일반 추론으로 도출되지 않는다. 5는 `내정업체`로 단정하지 않고 **관찰되는 경쟁 제한 가능성만 기록**한다는 원칙을 함께 둔다.

### 결정 3: 난이도와 주 라벨의 연결 규칙을 명시한다

> 난이도가 높다는 사실만으로 주 라벨을 올리지 않는다. **높은 난이도가 고급 기술자나 전문 인력의 추가 투입으로 이어질 때** `견적반영`한다.

주 라벨 도출 규칙:

- blocker 있음 → `계약·질의검토`
- blocker 없음 + 별도 장비·라이선스·수량·기간·외부 인증·전문 인력 또는 기본팀을 넘어서는 고급 기술 공수 → `견적반영`
- blocker 없음 + 기본 수행팀의 일반 분석·설계·개발·테스트 범위 → `통상수용`

이는 §8.2가 예고한 "위험 요인 분해 후 고정 규칙으로 주 라벨 산출"의 규칙 부분이며, 실무자가 명문화했다.

### 결정 4: 페르소나 판별 기준을 "기본 수행팀" 기준으로 구체화한다

결정 20의 "통상적인 중견 수행사"를 검사 가능한 형태로 대체한다.

> 기본적인 LLM·RAG 구축 역량을 가진 AI·IT 회사의 제안 담당자. 일반적인 분석·설계·개발·테스트는 기본 수행팀이 처리한다. **고급 기술자, 전문 인력, 별도 장비·라이선스가 필요하면 견적에 명시적으로 반영한다.**

"통상적인 회사인가"보다 "기본 수행팀으로 되는가"가 판정 가능한 질문이다. 컨설팅 요구사항 보정 기준(라벨별 예시)도 검토 기록의 것을 그대로 채택한다.

### 결정 5: 라벨 분포를 맞추기 위한 판정 변경 금지

> 라벨 분포를 맞추기 위해 판정을 바꾸지 않는다. 클래스 불균형은 표집, class weight와 평가 지표로 다룬다.

§11.9의 재확인이다. 앵커 풀 구축 시 `통상수용` 후보가 부족하다는 이유로 판정을 조정하려는 유혹이 발생할 수 있으므로 명문화한다.

### 부수 발견: `산출정보` 추출 누락

`korail_genai_isp_ismp:CSR-001` 검토 중 원본 요구사항 표의 `산출정보` 열이 `raw_requirement_text`에 포함되지 않았음이 확인됐다. 원본 Markdown 7개 문서에서 `산출정보`가 691회 등장하나 데이터셋 필드에 대응 항목이 없다.

산출물 목록은 견적의 직접 근거이므로 이 과제에서 특히 중요하다. §11.2(원문 변환 손실)에 해당하는 추출 결함이며 `scripts/data/build_dataset.py` 어댑터 조사가 필요하다. 데이터셋 재생성 시 `v0.3.0`으로 버전을 올린다.

## 22. 앵커 풀 v1 구축과 첫 few-shot 실행

### 배경: 사람 검토의 확장 한계

결정 21의 실무자 검토는 12건에 대해 높은 정보량을 냈으나, 앵커 풀에 필요한 규모로 확장하기 어렵다는 점이 확인됐다. 검토 대상이 늘수록 판단이 흐려지는 문제도 실무자 본인이 지적했으며, 이는 §10.3이 예고한 검토자 자기 일관성 문제와 같다.

전수 라벨링을 사람 검토 속도에 묶지 않기 위해, **반복 실행 일치를 자동 감사 기준으로 채택**한다.

### 결정 1: 앵커 출처를 두 등급으로 분리한다

| 등급 | 기준 | 라벨·근거 출처 |
|---|---|---|
| `검토완료` (사람 확정) | 실무자가 원문을 보고 판정 | 사람의 라벨과 근거 문장 |
| `모델일관_3of3` | 동일 입력 3회 실행에서 주 라벨이 3/3 일치 | LLM의 라벨과 근거 문장 |

두 등급은 `provenance` 필드로 구분해 기록하며 섞지 않는다. 논문에서는 등급별로 나눠 보고한다.

**근거 문장은 라벨과 같은 출처를 쓴다.** 사람이 확정한 라벨에 LLM 근거를 붙이면 모순된 앵커가 된다 — 예컨대 `ccrs_ai_platform:SFR-022`는 사람 판정이 `견적반영`인데 v5 근거는 "기본 수행팀이 처리 가능"이다.

### 결정 2: 앵커 풀 v1 구성

`data/anchors/anchor_pool_v1.jsonl`, 20건, 10개 문서 전체 포함.

| 라벨 | 사람확정 | 모델일관 | 계 |
|---|---:|---:|---:|
| 통상수용 | 7 | 0 | 7 |
| 견적반영 | 3 | 0 | 3 |
| 계약·질의검토 | 1 | 9 | 10 |

`계약·질의검토` 후보 10건은 문서·blocker 범주 다양성을 기준으로 선정한 뒤 3회 반복 실행했다.

- **주 라벨 3/3 일치: 10/10 (100%)**
- **`blockers` 조합 일치: 4/10** — 6건은 실행마다 blocker 구성이 달라졌다

주 라벨은 안정적이나 세부 분해는 흔들린다. §10.2의 반복 일치율 첫 측정치이며, 보조 축을 학습 타깃으로 쓸 때 이 불안정성을 감안해야 한다.

### 결정 3: 첫 few-shot 실행 결과 (층화 인출)

파일럿 40건, zero-shot v5 대비.

| zero \ few | 통상수용 | 견적반영 | 계약·질의검토 |
|---|---:|---:|---:|
| 통상수용 | 14 | 1 | 0 |
| 견적반영 | **3** | 5 | 1 |
| 계약·질의검토 | 0 | 1 | 14 |

- 일치 33/40 = **82%**, 판정 변동 7건 (결정 13의 Gemini 실험은 70.27% / 29.73%)
- 분포 변화 미미: 통상 15→17, 견적 9→7, 계약 15→16

**결정 14의 층화 인출이 검증됐다.** 결정 13에서 관측된 `견적반영` 68.7% 쏠림이 재현되지 않았다. 층화가 다수 라벨 편향을 실제로 억제한다.

**다만 사람 일치율은 하락했다: zero 10/11 → few 9/11.** 불일치 2건이 모두 `견적반영 → 통상수용` 방향이며, 전이 행렬에서도 이 방향이 최대 이동(3건)이다.

원인 가설: `견적반영` 앵커가 3건뿐이라 기준선이 약하고, 앵커 풀의 `통상수용` 7건이 모두 "일반적인 컨설팅 업무", "기본 수행팀이 처리한다" 톤이어서 매 프롬프트에 그 기준선이 실린다. `SFR-022`와 `SER-001`은 자신이 `견적반영` 앵커임에도 동일 문서 차단(결정 10)으로 자기 자신을 쓸 수 없어 다른 문서의 `통상수용` 앵커에 끌렸다.

### 기록된 한계

1. **등급 비대칭.** 세 라벨의 근거 강도가 다르다. `통상수용`·`견적반영`은 사람 확정, `계약·질의검토`는 10건 중 9건이 모델 일관성이다.
2. **`견적반영` 앵커 부족.** 3건뿐이며 층화 인출이 매번 이 중 하나를 뽑으므로 유사도가 낮은 앵커가 실릴 수 있다. 다음 개선 지점이다.
3. **fold별 풀 미구성.** §8.4는 fold마다 학습 문서만으로 풀을 구성하도록 요구하나, 현재 풀은 전체 문서에서 뽑았다. 파일럿 비교에는 허용되지만 전수 실험에서는 fold별 재구성이 필요하다.
4. **파일럿·풀 중복.** 파일럿 40건 중 16건이 앵커 풀에 포함된다. 동일 문서 차단으로 자기 자신은 인출되지 않으나, 다른 문서 타깃의 앵커로는 쓰인다.
5. **few-shot 반복 일관성 미측정.** 앵커링의 주 효과 주장은 일관성 개선인데(§8.3), few-shot의 반복 일치율은 아직 측정하지 않았다. zero-shot은 10/10을 확인했다.

### 미해결: zero-shot vs few-shot

현재 데이터로는 판정할 수 없다. 사람 일치율 차이는 11건 위의 1건이며, 그 11건은 v2→v3 변경분에서 나온 편향된 부분집합이다. 결정에는 §8.3이 정한 주 지표인 **반복 일관성 비교**가 필요하다.
