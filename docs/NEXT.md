## 1. 파인튜닝 v5 재학습 ← **여기부터**

현재 `reports/current/v4/finetune_*`는 전부 **v4 라벨** 기준이다. v5 최고 구성은 미정.

**왜 이것부터인가.** 지금까지 측정된 개입 중 측정 하한(0.016)을 넘는 것이 둘뿐이고
(파인튜닝+앙상블 +0.029, 문서 확충 +0.021), 그중 코드가 이미 있는 쪽이다.

### 최소 실행 — 앙상블 최고 조합의 두 멤버

v4 최고 앙상블은 `wc + ftB7 + ftL42`였다(fold 평균 0.643, 중첩 선택 10/10 안정).
`wc`는 TF-IDF라 CPU로 이미 있다. GPU가 필요한 건 나머지 둘이다.

```bash
RFP_DATASET_VERSION=v5 python -m scripts.modeling.finetune \
  --model klue/roberta-base --seed 7 --fold -1 \
  --epochs 6 --lr 2e-5 --batch-size 32 --grad-accum 1 --max-length 512
```

```bash
RFP_DATASET_VERSION=v5 python -m scripts.modeling.finetune \
  --model klue/roberta-large --seed 42 --fold -1 \
  --epochs 6 --lr 2e-5 --batch-size 8 --grad-accum 4 --max-length 512
```

`--fold -1`이 13 fold 전체다(도움말에 "10 fold"라고 적혀 있는데 옛말이다).
하이퍼파라미터는 v4 실행과 **같게 맞췄다** — 데이터셋만 바뀌어야 비교가 된다.
`large`가 `batch-size 8 × grad-accum 4`인 것은 메모리 때문이며 유효 배치는 32로 같다.

### 그다음 앙상블

```bash
RFP_DATASET_VERSION=v5 python -m scripts.evaluation.finetune_ensemble
```

앙상블은 **학습하지 않는다.** 저장된 OOF 예측을 묶기만 하므로 CPU로 몇 초다.
멤버 태그가 겹치면 멈추게 돼 있으니(`member_tag`), 태그 충돌이 나면 seed나 마스킹
표기를 확인한다.

### 기대치와 판정

| | v4 실측 | v5 기대 |
|---|---:|---:|
| word+char 단독 | 0.614 | **0.6395** (측정됨) |
| 최고 단일 파인튜닝 `ftL42` | 0.617 | ? |
| **최고 앙상블** | **0.643** | **~0.67** |

- 점수는 **fold 평균 macro F1**으로 읽는다. 통합 OOF는 같은 모델에서도 0.02쯤 높다.
- **측정 하한은 0.016이다**(fold 표준편차 0.0286, 평균의 SE 0.0079의 2배).
  이보다 작은 차이는 잡음이니 해석하지 않는다.
- 파인튜닝 **단독은 기준선과 거의 같을 것이다**(v4에서 0.617 대 0.614). 실망하지 말 것 —
  이득은 섞을 때 나온다.
- seed에 따라 흔들리므로 **단일 값이 아니라 범위로** 적는다.

## 2. 보조 헤드 — **이미 해봤고 효과가 없다** (순위 내림)

`aux-heads` 브랜치에 **다중 헤드가 이미 구현돼 있고 v4에서 5회 돌렸다.**
`scripts/modeling/finetune.py`의 `MultiHeadModel`, `AUX_HEADS`, `--aux`, `--aux-weight`.
보조 축은 `blockers`(다중 라벨 BCE) + `cost_basis` + `build_difficulty` +
`domain_dependency`이고, 인코더의 `[CLS]` 표현을 공유한다.

결과가 신통치 않다. `reports/current/v4/finetune_results.md`(aux-heads 브랜치) 기준이며,
결정 기록은 `docs/history/decisions-09.md` 2026-09-07 09:30에 있다.

| 설정 | +aux | 원본 | 차이 | 경계 혼동 |
|---|---:|---:|---:|---:|
| base seed 42 | 0.588 | 0.573 | +0.015 | 118 (원본 111) |
| base seed 7 | 0.594 | 0.609 | **-0.015** | 105 (104) |
| base seed 13 | 0.589 | 0.597 | -0.008 | 112 (104) |
| large seed 42 | 0.573 | 0.617 | **-0.044** | 113 (107) |
| large seed 7 | 0.604 | 0.595 | +0.009 | 105 (98) |

**부호가 오가고 평균 -0.009다.** 전부 측정 하한(0.016) 근처이거나 아래이고, 경계 혼동은
오히려 늘었다. 보조 축을 주는 것으로는 안 된다는 것이 v4에서 이미 나왔다.

남은 변형은 보조 헤드의 타깃을 **v5/v6 소프트 분포**로 바꾸는 것이다
(Fornaciari et al., NAACL 2021 `2021.naacl-main.204` — 주 과제는 하드 라벨 유지,
보조 헤드가 분포를 KL로 예측). 앞서 한 번 돌린 -0.047은 하드 라벨을 소프트 분포로
**대체**한 것이라 그 논문의 방법이 아니고 판정도 아니다.

**그래도 우선순위는 낮다.** 같은 구조에서 보조 축 넷이 모두 실패했고, 타깃만 바꿔
0.016을 넘길 근거가 약하다. 1번과 3번을 먼저 하고, 여력이 남으면 본다.

구현하려면 `aux-heads`의 `finetune.py`에서 `MultiHeadModel` 계열을 가져와야 한다.
**단, 두 브랜치의 `finetune.py`가 갈려 있어 자동 병합이 안 된다**(aux-heads에는
`run_id`가 없고, main에는 `MultiHeadModel`이 없다). 통째 병합 말고 필요한 부분만
옮긴다.

## 3. 문서 +3개 (GPU 불필요, 약 $4)

학습곡선 `macroF1 = 0.0896·ln(학습문서수) + 0.4241`(가중 R² 0.969).
11문서 예측 0.6390 대 실측 0.6395로 검증됐다.

| 총 문서 | 추가 | 예상 | 현재 대비 |
|---:|---:|---:|---:|
| 16 | +3 | 0.661 | +0.021 |
| 19 | +6 | 0.678 | +0.039 |
| 24 | +11 | 0.701 | +0.062 |

**최소 3개를 한 번에 넣어야 한다.** 1~2개는 이득(0.007~0.014)이 측정 하한 아래라
올랐는지 아닌지도 모른다.

라벨링 배치가 421건에 $3.83이었으니 문서당 약 $1.3. 문서는 나라장터에서 구한다.
**실행 전 사용자 확인 필요**(유료 API).

절차는 `docs/history/decisions-07.md` 2026-09-07 03:04 항목에 있다. `.hwp`·`.xlsx`
모두 `scripts/data/hwp_tables.py`·`xlsx_tables.py`로 원본에서 직접 표를 읽는다.

## 알아둘 것

- **경계 혼동은 어떤 개입으로도 안 움직인다.** v5에서 127건(오답의 32%)이고,
  v4에서 앙상블이 오답을 39건 줄이는 동안 경계는 98 → 97로 한 건 줄었다.
  점수가 오르더라도 이득은 경계 밖에서 나온다. 자세한 것은
  `notebooks/20_boundary_cases.ipynb`.
- 테스트는 **292 통과 / 3 실패**가 정상이다. 실패 3건은 전부 기존 문제 —
  `fasttext-wheel`이 py3.13 빌드가 없고, `05_finetune_analysis.ipynb`가 셀 24개에
  번호가 `05_`로 중복이라 노트북 테스트 2건을 깬다. 그대로 두기로 했다.
- 실행 조건은 `run_id`가 자동으로 박는다(`roberta-large.s42.len512.v5` 꼴).
  결과 파일을 열면 어느 데이터셋으로 돌렸는지 확인할 수 있다.
