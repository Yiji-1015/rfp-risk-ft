# 007. `산출정보` 열 누락

**상태**: 수용 (이득이 비용에 못 미침 — 결정 30)

## 관측

원본 요구사항 표의 `산출정보` 열이 데이터셋에 반영되지 않았다. 산출물 목록은 견적의
직접 근거이므로 결함으로 기록해두었으나, 실측하면 **이득이 크지 않다.**

| 문서 | 칸 | 채워짐 |
|---|---:|---:|
| 신용회복위원회 | 95 | 95.8% |
| 침해대응체계 | 67 | 89.6% |
| 강원랜드 | 50 | 64.0% |
| 남동발전 | 101 | 54.5% |
| KEXIM | 137 | 43.8% |
| 식약처 | 192 | 34.4% |
| 국방·한국공항공사·인천공항 | 0 | — |

열이 존재하는 요구사항이 642건, 그중 값이 채워진 것이 364건. **전수 1,024건 대비 35.5%**다.
나머지는 `<td>산출정보</td><td></td>`처럼 칸만 있고 비어 있다.

## 영향

- 정보가 적은 것보다 **문서 편중이 문제다.** 95.8%인 문서와 0%인 문서가 공존한다.
  이 필드를 특징으로 넣으면 문서와 상관된 특징이 하나 늘고, 이미 2.8배인 fold 난이도
  편차(→ [003](003-document-label-imbalance.md))가 더 커진다.
- 실무적으로도 산출정보 칸은 관행적으로 채워두는 항목이라 판정에 영향이 작을 개연성이 높다.

## 대응

**전수 재라벨링을 하지 않는다.** 넣으려면 `requirements_v0.3.0` 재생성 + 재라벨링(약 9,000원)이
필요한데, 얻는 것은 35.5% 커버리지의 편중된 필드 하나다. 반대로 잃는 것이 크다 —
결정 23의 반복 기준선, 결정 28의 3자 비교, 앵커 풀 v2와의 정합성이 모두 `v0.2.0` 입력 기준이다.

판단이 필요해지면 순서는 이렇다.

1. 추출만 먼저 한다 (무료)
2. 산출정보를 프롬프트에 넣은 **100건 파일럿** (약 800원)
3. 기존 라벨과 비교해 결정 23의 반복 기준선 **92.5%** 안에 들면, 산출정보는 라벨을
   바꾸지 않는다는 뜻이고 논의는 끝난다

9,000원을 눈감고 쓰는 대신 800원으로 답을 사는 순서다.
