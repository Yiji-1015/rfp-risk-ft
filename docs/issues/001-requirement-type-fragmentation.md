# 001. `requirement_type` 표기 분열

**상태**: 미해결

## 관측

`requirement_type`이 **60종**이다. 같은 개념이 문서마다 다르게 적혀 있고, 추출기가
원문 표기를 그대로 옮기기 때문이다.

```
기능 요구사항 (97) / 기능 (60) / 기능 요구사항(SFR) (38) / 기능요구사항 (7)
프로젝트 관리 요구사항 (42) / 프로젝트관리 요구사항 (30) / 프로젝트관리 (26)
  / 프로젝트 관리 (11) / 프로젝트 관리 요구사항(PMR) (10) / 프로젝트 관리(PMR) (5)
```

괄호 안 코드 제거, 공백 제거, `요구사항` 접미어 제거만 해도 **60종 → 28종**으로 줄어든다.

```python
import re
def normalize(t):
    if not t:
        return '(미지정)'
    return re.sub(r'\([A-Z]{2,4}\)', '', t).replace(' ', '').replace('요구사항', '') or '기타'
```

정규화 후 상위: 기능 202 / 프로젝트관리 124 / (미지정) 101 / 보안 78 / 데이터 71 /
프로젝트지원 61 / 제약사항 54 / 품질 46 / 인터페이스 45 / 성능 41

## 영향

- **유형별 분석이 성립하지 않는다.** "기능 요구사항"의 통상수용 비율이 48.5%인데
  "기능"은 35.0%, "기능 요구사항(SFR)"은 10.5%다. 셋은 같은 유형인데 서로 다른 값이
  나오는 이유는 유형이 아니라 **어느 문서에서 왔는지**가 다르기 때문이다.
  표기가 문서와 얽혀 있어 유형 효과와 문서 효과가 분리되지 않는다.
- 유형을 특징으로 쓰면 사실상 문서 ID를 넣는 것과 비슷해진다. 문서 단위 fold에서
  누수에 가깝게 동작한다.

## 대응

지금은 **정규화하지 않았다.** `label_dataset_v1`은 라벨 기록이고, 여기에 내 판단이
들어간 파생 필드를 섞으면 동결 산출물의 성격이 흐려진다.

정규화는 라벨을 건드리지 않는 파생 작업이라 **재라벨링 없이 언제든 추가할 수 있다.**
쓰기로 하면 `requirement_id` 접두어(SFR·PMR·SER 등)와 대조해 교차 검증한 뒤
`requirement_type_normalized`를 별도 필드로 붙인다.

접두어 쪽이 더 신뢰할 만한 후보다. 문서 안에서 일관되게 부여되고 이미 앵커 후보
표집(§4-1)에서 5개 카테고리 분류에 쓰고 있다.
