# 001. `requirement_type` 표기 분열

**상태**: 해결 (`label_dataset_v3`, 결정 32 및 2026-08-25 기록)

> 학습 입력이 요구사항 원문뿐이라면 유형은 특징이 아니다(→ [README](README.md)의 전제).
> 그래도 정규화가 필요한 이유는 **분석과 층화** 때문이다. 유형별 경향을 못 읽으면
> fold 배정도 라벨 검토도 근거 없이 하게 된다.

## 관측

`requirement_type`이 **60종**이었다. 추출기가 문서의 표기를 그대로 옮기기 때문에
같은 개념이 문서마다 다르게 남았다.

```
기능 요구사항 (97) / 기능 (60) / 기능 요구사항(SFR) (38) / 기능요구사항 (7)
프로젝트 관리 요구사항 (42) / 프로젝트관리 요구사항 (30) / 프로젝트관리 (26)
  / 프로젝트 관리 (11) / 프로젝트 관리 요구사항(PMR) (10) / 프로젝트 관리(PMR) (5)
```

그래서 같은 유형이 서로 다른 값을 냈다.

| 표기 | 건수 | 통상수용 |
|---|---:|---:|
| 기능 요구사항 | 97 | 48.5% |
| 기능 | 60 | 35.0% |
| 기능 요구사항(SFR) | 38 | 10.5% |
| 기능요구사항 | 7 | 0.0% |

넷은 같은 유형이다. 차이는 유형이 아니라 **어느 문서에서 왔는지**였다.

## 왜 접두어만으로는 안 되는가

`requirement_id` 접두어(SFR·PMR·SER…)가 더 일관돼 보이지만, **문서를 넘어 충돌한다.**
`kexim_ai_platform` 한 문서가 표준 접두어를 다른 뜻으로 쓴다.

| 접두어 | 다수 문서 | kexim |
|---|---|---|
| `INR` | 인터페이스 (5개 문서) | **인프라** |
| `ECR` | 시스템장비구성 (5개 문서) | **ECM** |
| `SER` | 보안 (9개 문서) | **서비스** |

그래서 **표기가 접두어보다 우선**한다. 문서가 스스로 밝힌 분류가 접두어 관행보다
사실에 가깝다. 접두어는 표기가 아예 없는 문서에서만 대체로 쓴다.

## 해결

[`scripts/labeling/requirement_taxonomy.py`](../../scripts/labeling/requirement_taxonomy.py)가
정본 분류로 정규화한다. 정본은 **공공 SW 제안요청서 표준 11분류 + `컨설팅`**이다.
컨설팅은 표준에 없지만 ISP·ISMP 요구사항은 판정 기준이 뚜렷이 다르고 프롬프트에도
별도 보정 블록이 있어(결정 21) 합치면 정보가 사라진다.

`label_dataset_v3`에 두 필드가 들어 있다.

- `requirement_type_normalized` — 정본 유형 (60종 → **12종**, 미매핑 0건)
- `requirement_type_source` — 판단 근거 (`text` 1,024 / `prefix` 0 / `none` 0)

원본 `requirement_type`은 **지우지 않고 그대로 둔다.** 매핑을 나중에 재검증할 수 있어야 한다.

## 결과

정규화하니 통상수용 비율이 **단조롭게 정렬된다.**

| 정본 유형 | 건수 | 문서수 | 통상수용 |
|---|---:|---:|---:|
| 시스템장비구성 | 78 | 6 | 1.3% |
| 성능 | 45 | 9 | 17.8% |
| 기능 | 277 | 9 | 36.1% |
| 테스트 | 41 | 9 | 43.9% |
| 프로젝트지원 | 71 | 10 | 50.7% |
| 보안 | 88 | 10 | 55.7% |
| 컨설팅 | 22 | 6 | 59.1% |
| 데이터 | 77 | 10 | 59.7% |
| 인터페이스 | 48 | 9 | 68.8% |
| 제약사항 | 62 | 10 | 72.6% |
| 품질 | 64 | 10 | 75.0% |
| 프로젝트관리 | 151 | 10 | 76.2% |

원가가 붙는 유형(장비·성능)이 낮고 표준 문구가 많은 유형(프로젝트관리·품질)이 높다.
**60종으로 흩어져 있을 때는 보이지 않던 순서다.**

## 남은 한계

- `시스템장비구성`(6개 문서)과 `컨설팅`(6개 문서)은 여전히 일부 문서에만 나타난다.
  이 둘은 유형 효과와 문서 효과가 완전히 분리되지 않는다. 노트북이 문서 8개 미만
  유형을 따로 표시한다.
- 매핑에는 판단이 들어갔다. `ECM`→기능, `안전`→제약사항, `거버넌스및PMO`→프로젝트관리
  같은 결정은 `requirement_taxonomy.py`에 근거를 주석으로 남겼다.
- 새 문서가 새 표기를 가져오면 `기타`로 떨어지고 테스트가 실패한다. 조용히 최빈값으로
  채우지 않는다.
