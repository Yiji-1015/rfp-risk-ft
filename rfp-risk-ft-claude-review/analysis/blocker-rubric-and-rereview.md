# Blocker 기준 및 12건 재검토 기록

## 재검토 범위

- 현재 요구사항의 명칭, 유형, 정의와 세부내용만 사용한다.
- 산출정보, 연결 요구사항과 문서 전체 문맥은 판단에 사용하지 않는다.
- 본문에 없는 조건은 추론하지 않는다.
- `내정업체`라고 단정하지 않고, 요구사항에서 관찰되는 특정 제품·공급자 종속 또는 경쟁 제한 가능성만 기록한다.

## 기준 페르소나

기본적인 LLM·RAG 구축 역량을 가진 AI·IT 회사의 제안 담당자다. 일반적인 분석·설계·개발·테스트는 기본 수행팀이 처리한다고 가정한다. 고급 기술자, 전문 인력, 별도 장비·라이선스가 필요하면 견적에 명시적으로 반영한다. 도메인 지식은 주 라벨과 분리된 보조 축으로 평가한다.

### 컨설팅 요구사항 보정 기준

기준 수행사는 일반적인 ISP·ISMP와 AI 구축 컨설팅 경험을 보유한다고 가정한다.

- `통상수용`: 비전·KPI·전략과제 수립, 현황·업무프로세스 분석, 연동 가능성 검토, 일반적인 조직·정책·운영절차 설계, 표준 아키텍처와 MCP 연계 원칙 정의
- `견적반영`: 기본 컨설팅팀을 넘어 AI 모델 평가, GPU·클라우드·보안 아키텍처, 복잡한 데이터 설계, FP·M/M 및 예산 산정처럼 고급·복수 전문인력을 명시적으로 투입해야 하는 범위가 요구사항에 드러남
- `계약·질의검토`: 인증 대상·비용·기간·합격 기준이 없는 실제 외부 인증 취득, 계약 후 세부 범위 확정, 기술 실현성·라이선스·공급 가능성 확인, 포괄 책임 또는 특정 공급자 종속 가능성처럼 입찰 전 확인이 필요한 blocker가 요구사항에 드러남

기술명이 등장한다는 이유만으로 난이도를 높이지 않는다. 예를 들어 MCP 구조의 정의·설계만 요구하면 통상 컨설팅으로 보고, 실제 구현·인증·운영·성능 책임이 함께 요구될 때 별도 원가나 blocker를 검토한다. 다른 요구사항이나 문서 전체를 봐야 알 수 있는 불확실성은 현재 요구사항의 주 라벨에 반영하지 않는다.

## Blocker 정의

`blocker`는 비용이 발생한다는 뜻이 아니라, 제안·입찰 전에 반드시 확인해야 안전하게 수용할 수 있는 조건을 뜻한다.

1. 범위·책임: 열린 범위, 포괄 책임, 발주기관 재량에 따른 추가 수행, 무제한 의무
2. 검수·성능 기준: 합격 기준 부재, 주관적 검수, 합격할 때까지 반복 보완, 결과 보증
3. 기술 실현성: 현재 기술이나 주어진 환경에서 충족 가능 여부를 먼저 검증해야 하는 조건
4. 라이선스·공급 가능성: 요구 제품·모델·장비·라이선스의 실제 조달 또는 사용 가능성이 불명확한 조건
5. 특정 제품·공급자 종속 가능성: 과도하게 구체적인 규격·실적·호환 조건 때문에 충족 가능한 공급자가 제한될 수 있는 조건

## 주 라벨 연결

- blocker 있음: `계약·질의검토`
- blocker 없음 + 별도 장비·라이선스·수량·기간·외부 인증·전문 인력 또는 기본팀을 넘어서는 고급 기술 공수: `견적반영`
- blocker 없음 + 기본 수행팀의 일반 분석·설계·개발·테스트 범위: `통상수용`

구축 난이도와 도메인 의존성은 보조 축이다. 난이도가 높다는 사실만으로 주 라벨을 올리지 않는다. 높은 난이도가 고급 기술자나 전문 인력의 추가 투입으로 이어질 때 `견적반영`한다. 도메인 의존성은 별도 기록하며, 요구사항 본문에서 도메인 정보 부재가 수행을 막는다고 관찰될 때만 blocker를 검토한다.

라벨 분포를 맞추기 위해 판정을 바꾸지 않는다. 클래스 불균형은 표집, class weight와 평가 지표로 다룬다.
