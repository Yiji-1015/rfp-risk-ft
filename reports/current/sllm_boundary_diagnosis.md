## 5. 실제로 사업별 확인이 필요한 사례도 있습니다

전체 352토큰으로 잘리지 않습니다. 국방망 안에서 코드 생성·수정·실행 확인 등을 제공해야 합니다.

실무 판단에 필요한 추가 정보는 다음과 같습니다.

- 도입하려는 모델·IDE 플러그인의 오프라인 배포 및 라이선스 조건
- 실제 반입·운영 허용 조건과 사용할 수 있는 장비

‘폐쇄망이니 불가능하다’고 단정할 수 없습니다. 반대로 ‘로컬 모델이 있으니 견적만 잡으면 된다’고 확정할 수도 없습니다.
후보 솔루션과 운영 조건을 확인해야 두 판단을 구분할 수 있습니다. 이번 분석에서는 제품 조달 가능성을 조사하거나 확정하지 않았습니다.

### 신용회복위원회 `SFR-012` 플랫폼·모델 통합관리

사용자는 이전 검토에서 ‘하나하나 뜯어보면 견적반영 같다’고 판단했습니다.
그러나 v7 정답도 계약검토로 남았습니다. v7의 근거는 오프라인 모델 반입과 외부 API 금지에 따른 공급 확인입니다.

이 사례는 모델의 오답이라고만 설명하기 어렵습니다. **사용자의 수용 기준과 정답표의 보수적인 공급 판단이 다릅니다.**
필요한 확인은 ‘오프라인 사용 가능한 후보 모델과 권리가 이미 확보됐는가’입니다.
동시에, 별도 공급 불확실성이 명시되지 않아도 오프라인 조건만으로 blocker를 줄 것인지 판단 기준을 합의해야 합니다.
전체 943토큰이라 입력 절단도 함께 존재합니다. 원인을 하나로 분류하지 않았습니다.

## 6. 다음 판단의 순서

이번 결과만으로 GPU 재학습이나 추가 라벨링을 시작할 근거는 충분하지 않습니다.

1. **누락된 근거부터 확인합니다.** 위 세 사례는 전체 조항과 512토큰 입력을 비교할 명확한 이유가 있습니다. 이 사례들로 입력 길이를 정한 뒤 같은 평가셋의 점수 상승을 독립 검증처럼 제시해서는 안 됩니다.
2. **정답표 재현과 실무 수용 판단을 구분합니다.** 식약처 성능 수치는 전자, 오프라인 솔루션 공급 여부는 후자의 질문입니다.
3. **규칙이 엇갈리는 사례만 사람이 확인합니다.** 모델 이름을 바꾸기 전에, 어떤 증거가 있으면 견적반영을 허용할지 적는 것이 우선입니다.

이미 시행한 문서 맥락 카드 실험은 공통 성공 82건에서 8건 개선·3건 악화, 경계 표본 7건에서는 정답 3건으로 동일했습니다.
따라서 ‘문서 요약을 더 붙이면 된다’는 처방을 반복할 근거도 없습니다. 이번에 찾은 것은 사업 개요보다 구체적인 누락 문장과 확인 항목입니다.

이 분석의 결론은 ‘큰 모델이 쓸모없다’도 ‘길이만 늘리면 해결된다’도 아닙니다.
**읽지 못한 정보, 읽었지만 적용하지 못한 규칙, 사람도 합의가 필요한 판단을 나눠야 다음 실험이 의미가 있습니다.**
